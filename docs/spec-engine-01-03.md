# Engine Spec: items 1–3

Three engine-only items. No TUI work, no network, no new dependencies expected.
Each is independently shippable and gated by `make ci`.

All three are held to the **Engine standards** section of `CLAUDE.md`: typed
`Diagnostic`s not strings, no silently-skipping tests, properties where an
invariant exists, no network in tests ever, fixtures generated by
`crates/corpus` rather than hand-written, tracing that never puts highlight text
above `trace!`.

---

## Item 1 — KOReader format work

Split in two. **1a produces a document, 1b produces code.** 1a must come first
because its answer decides 1b's schema.

### 1a. Format investigation → `docs/koreader-format.md`

No code. Three sources, in order of authority:

1. **KOReader source.** `frontend/apps/reader/modules/readerannotation.lua`,
   `frontend/docsettings.lua`, `frontend/apps/reader/modules/readerstatistics.lua`.
   This is the spec; a fixture is only ever evidence.
2. **Real sidecars, minted locally.** KOReader ships desktop builds (Linux
   AppImage, macOS). Run it against the epubs already in `epubs/`; make
   highlights, notes, a rating and a summary; close the book; harvest the
   `.sdr`. This satisfies the standing rule that fixtures must not be generated
   by our own parser — here the generator is the reference implementation.
   Drop the results in `crates/engine/tests/fixtures/koreader/real/`
   (gitignored).
3. The user's own device export, for realism the synthetic tiers can't reach:
   long books, hundreds of highlights, CJK, a legacy-format sidecar.

**Questions the document must answer:**

- **Does editing an annotation's note change its `datetime`?** This is the
  blocking one. It decides item 2's whole shape:
  - *No* → the hash is stable, a note edit is silently dropped, and item 2's
    targeted-update fix is correct as designed.
  - *Yes* → the hash changes and the **same highlight re-imports as a duplicate
    row**. Conflict handling cannot fix that; the identity hash would have to
    drop `ko_datetime` and key on `pos0` + `text`, which is a far bigger change
    with its own collision questions.
- Exact shape of `summary`: field names, the `status` value set (expected
  `reading` / `complete` / `abandoned`, possibly `tbr` on newer builds), the
  rating's range and type, whether `note` there is the user's review.
- `percent_finished` — type and range (expected 0.0–1.0 float at sidecar root).
- The `stats` subtable: which fields, and confirm `md5` is the same value as the
  root `partial_md5_checksum`.
- `util.partialMD5`'s algorithm — needed later for item 12, not for this item.
- Whether the legacy (pre-`annotations`) format carries any of the above.

### 1b. Parse and expose

`KoSidecar` (`crates/engine/src/koreader.rs:34`) already carries `title`,
`authors`, `language`, `partial_md5` and `highlights`.

**Note:** `partial_md5` is *already parsed* from the root
`partial_md5_checksum` key (`koreader.rs:78`) and then never used. It does not
need to be computed for device matching — only for owning our own files, which
is item 12. Item 3 can use it immediately.

Add to `KoSidecar`:

```rust
pub percent_finished: Option<f64>,   // 0.0..=1.0, sidecar root
pub summary: Option<KoSummary>,      // the device's own status/rating/review
pub stats: Option<KoStats>,          // title, authors, pages, series, language, md5,
                                     // total_time_in_sec, highlights, notes
```

`KoSummary` fields per 1a. `status` is a typed enum with an `Other(String)`
fallback — an unknown status from a future KOReader must degrade, never fail the
import.

**Persistence in this item: `partial_md5` only**, via the mapping table below.
Rating, status and `percent_finished` are carried in the parse result and in
`ImportReport`, but have nowhere correct to live until `readings` exists
(item 4). Do not park them on `books` — that column set is about to move.

```sql
-- migration 0003_device_books.sql
CREATE TABLE device_books (
    partial_md5 TEXT PRIMARY KEY,
    book_id     INTEGER NOT NULL REFERENCES books(id) ON DELETE CASCADE,
    linked_by   TEXT NOT NULL,     -- 'auto' | 'manual'
    first_seen  INTEGER NOT NULL,
    last_seen   INTEGER NOT NULL
);
CREATE INDEX idx_device_books_book ON device_books(book_id);
```

`match_book` gains a first branch: **`partial_md5` → `device_books` → book_id**,
ahead of the sibling-epub ISBN lookup and the fuzzy title match. `MatchMethod`
gains `Md5`.

### Fixtures and tests

New synthetic cases via `crates/corpus/src/synthetic.rs` (`make synthetic`),
each with a golden:

- `Summary.sdr` — a sidecar with `summary` (status, rating, review note) and
  `percent_finished`.
- `Stats.sdr` — a sidecar with a full `stats` subtable.
- `SummaryLegacy.sdr` — legacy layout, whatever 1a establishes it carries.
- `SummaryUnknownStatus.sdr` — a `status` value we've never seen. Must import
  cleanly and round-trip as `Other`.

Tests: parse assertions per fixture; `match_book` prefers `Md5` over `Title`
when a mapping exists; an unknown status does not fail an import.

### Done when

`docs/koreader-format.md` exists and answers the `datetime` question; `make ci`
green; the four fixtures and goldens are committed; `partial_md5` matching works
end to end.

## Item 2 — The highlight ownership seam

**Blocked on 1a's `datetime` answer.** The spec below assumes *no* — that a note
edit leaves `datetime` alone. If 1a says otherwise, stop and re-plan the
identity hash first.

### Migration

```sql
-- migration 0004_highlight_ownership.sql
ALTER TABLE highlights RENAME COLUMN note TO ko_note;   -- theirs
ALTER TABLE highlights ADD COLUMN annotation TEXT;      -- ours, never touched by import
ALTER TABLE highlights ADD COLUMN last_seen_ko_note TEXT;
```

`last_seen_ko_note` is not used yet. It exists so a future two-way sync can tell
"the user changed it here" from "the device changed it there" — a distinction
that is unrecoverable if only the merged result is ever stored.

### Storage

Leave `insert_highlight` **exactly as it is** — `ON CONFLICT … DO NOTHING`
(`crates/engine/src/storage/highlights.rs:55`). Turning it into `DO UPDATE`
makes `RETURNING id` yield a row on the conflict path too, so `Some(id)` stops
meaning "newly inserted" and the `inserted`/`skipped` counts the goldens assert
collapse into each other.

Add a second method instead:

```rust
/// Refresh device-owned payload on an existing highlight. Returns true if any
/// column actually changed. Straight assignment, not COALESCE: a sidecar is the
/// complete state of the annotation, so a missing note means the user deleted
/// it. (The books upsert's COALESCE no-clobber is right for providers, which
/// return partial records, and wrong here.)
pub async fn refresh_device_fields(
    &self, book_id: i64, h: &NewHighlight,
) -> Result<bool>
```

Updates `ko_note`, `color`, `chapter`, `page`, and sets
`last_seen_ko_note = h.note`. Must compare before writing so the return value —
and therefore the counter — is accurate. Must never touch `annotation`,
`source`, `created_at`, or `id`.

Import becomes: insert → on `None`, `refresh_device_fields` → count.

### Report

```rust
pub struct BookImportStats {
    pub book_id: i64,
    pub book_title: String,
    pub inserted: usize,
    pub updated: usize,     // NEW
    pub skipped: usize,
    pub flashcards: usize,
    pub matched_by: MatchMethod,
}
```

`updated` counts rows whose device-owned fields changed. `skipped` narrows to
"present and identical". CLI import output gains the count.

### Fixture

`crates/corpus/src/synthetic.rs` gains `variants/Pachinko-NoteEdited.sdr` —
byte-identical to `Pachinko.sdr` except one existing annotation's note text.

Sibling to the existing `variants/Pachinko-Superset.sdr`, and for the same
recorded reason: **a committed fixture, not a string splice.**

### Tests — the invariant splits three ways

The existing `reimport_is_strictly_idempotent`
(`crates/engine/tests/koreader_import.rs:300`) is **not wrong** and stays. It
re-imports an identical fixture, and identical bytes genuinely should change
nothing. What it cannot do is distinguish "nothing should have changed" from "we
discard device updates" — because that fixture contains no device update.

1. `reimport_is_strictly_idempotent` — unchanged. Identical bytes → nothing
   changes anywhere.
2. `device_edits_refresh_but_ours_survive` — import `Pachinko.sdr`, set an
   `annotation` on the edited highlight, import `Pachinko-NoteEdited.sdr`.
   Assert: `inserted == 0`, `updated == 1`, `ko_note` is the new value,
   `annotation` unchanged, `created_at` unchanged, `source` unchanged.
3. `highlight_ids_are_stable_across_refresh` — capture ids before, assert
   identical after. **This is the one that would really hurt:**
   `notes.highlight_id` and `flashcards.highlight_id` are foreign keys
   (`0001_init.sql:48`, `:67`), so a delete-and-reinsert refresh would silently
   null note anchors and cascade flashcards away. Assert it, don't assume it.

Regenerate goldens: `make synthetic` then `make golden`.

### Done when

`make ci` green; `updated` visible in CLI import output; the three tests above
pass; goldens regenerated and reviewed as a diff (the counter change should be
the only semantic difference).

## Item 3 — `import_book_from_sidecar`, link and merge

Today, a device book that isn't in the library is reported and **dropped**
(`crates/engine/src/koreader.rs:392`) — import only ever attaches highlights to
books that already exist. So "pull this book in from the reader", the primary
verb of the device screen, has no engine support at all.

**Fully offline.** No provider enrichment in v1 — deferred by decision — which
also means no mock provider is needed and the "no network in tests" rule is
satisfied trivially.

### Create from sidecar

```rust
/// Create a book from a sidecar's own metadata and import its highlights.
/// Offline: title/authors/page_count/language come from the sidecar's `stats`
/// table, falling back to `doc_props`. The book has no ISBN, cover or
/// description — the user enriches later via search, then merges.
pub async fn import_book_from_sidecar(
    storage: &Storage, sidecar: &Path,
) -> Result<BookImportStats>
```

**Idempotency does not come from `upsert_book`.** `books.rs:90` branches
isbn_10 → isbn_13 → *plain insert*, and a sidecar-seeded book has neither ISBN,
so it takes the unconditional-insert branch every time. Calling this twice
without a guard produces two books.

So: check `device_books` by `partial_md5` first. Known → use that `book_id`.
Unknown → create, then record the mapping with `linked_by = 'auto'`.

If a sidecar has no `partial_md5`, fall back to creating and mapping nothing —
and say so in the report, because that book will be re-created on a second pull.
A `Diagnostic` variant, not a bare warning string.

### Candidate matching

`match_book` currently auto-links at jaro-winkler ≥ 0.85 and everything below is
silently "New" — so a variant title quietly becomes a duplicate.

```rust
pub struct MatchCandidate { pub book_id: i64, pub title: String, pub score: f64 }

/// Books in the ambiguous band, best first. Above AUTO_MATCH the caller should
/// have matched already; below CANDIDATE_MIN it's noise.
pub async fn match_candidates(
    storage: &Storage, sc: &KoSidecar,
) -> Result<Vec<MatchCandidate>>
```

`AUTO_MATCH = 0.85` (existing), `CANDIDATE_MIN = 0.60`. Both `const`, not
config — same reasoning as `PROVIDER_TIMEOUT`.

Matching order overall: **`device_books` md5 → sibling-epub ISBN → title ≥ 0.85
→ candidate band → New.**

### Link and merge

```rust
/// Record a sidecar↔book decision so it is never re-guessed.
pub async fn link_sidecar(storage: &Storage, partial_md5: &str, book_id: i64) -> Result<()>;

/// Fold `src` into `dst`: move highlights, notes, flashcards and device_books
/// rows, merge book fields COALESCE-style (dst wins on conflict), delete `src`.
pub async fn merge_books(storage: &Storage, src: i64, dst: i64) -> Result<MergeReport>;
```

`merge_books` exists because the ISBN-less insert path guarantees duplicates
will occur regardless of how good matching gets. It must run in **one
transaction**, and must handle the highlight identity collision: an identical
highlight already on `dst` is dropped, not duplicated — recompute
`identity_hash` against the new `book_id`, since `book_id` is one of its inputs
(`storage/highlights.rs:22`).

### Tests

All `sqlite::memory:`, all offline.

- Pull an unmatched sidecar → book created with sidecar title/authors/pages,
  highlights attached, `device_books` row written.
- Pull twice → second is a no-op (`inserted == 0`, one book, not two).
- Sidecar with no `partial_md5` → still imports, emits the diagnostic.
- `match_candidates` returns a near-miss title in the band and excludes both an
  exact match and unrelated noise.
- `link_sidecar` then re-pull → matched by `Md5`, no duplicate.
- `merge_books` moves everything, deletes `src`, and drops a highlight that
  collides on identity rather than duplicating it.
- Property: merge is idempotent — merging `src` into `dst` twice equals once.

### Done when

`make ci` green; `unmatched` is an actionable state rather than a dead end;
pulling the same device twice creates one book.

## Order and dependencies

```
1a (document; answers the datetime question)
 ├──> 1b (parse + device_books + Md5 matching)
 │     └──> 3 (pull from device; needs device_books)
 └──> 2  (ownership seam; schema depends on 1a's answer)
```

2 and 3 are independent of each other and can be done in either order. Both
depend on 1. Nothing here touches the TUI; the device screen (item 6) is the
first frontend work and is not part of this spec.
