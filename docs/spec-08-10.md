# Spec: items 8–10

Items 1–7 are on `main` (`303320a`). This spec carries the currently-reading
home screen, the backlinks pane, and Goodreads CSV in and out.

Everything is held to the **Engine standards** section of `CLAUDE.md`: typed
`Diagnostic`s not strings, no silently-skipping tests, properties where an
invariant exists, no network in tests ever, fixtures generated by
`crates/corpus` rather than hand-written, and tracing that never puts highlight
text, note bodies or search queries above `trace!`.

Two things changed before this spec that shape it:

- **The gate is real now.** CI runs `--workspace --locked` on ubuntu, so a TUI
  change is tested on every PR. `make ci` reproduces it. There is a
  `cargo-tester` agent, and it now exists rather than merely being referenced.
- **The local database does not matter.** The user has said so explicitly. A
  destructive migration no longer needs verifying against a copy of a real
  `database/app.db`, which retires the most awkward constraint of the item-4
  era. Migration *numbering* discipline survives and is now mechanised:
  `migration_versions_are_contiguous_from_one` plus a PR job refusing an edited
  migration.

## One erratum before anything is planned against the build order

**Item 8 is not implementable as written.** `docs/decisions.md` says
"Currently-reading home screen; action = open the reflection" — and the TUI has
*no reflection or review surface at all*. `grep -r reflection crates/tui/src`
finds one comment. Item 7 was scoped engine-plus-CLI with its TUI half deferred
and never given a number.

That deferred half is item 8's action, so it is folded into **8b** rather than
being given one. Doing them separately means two passes over the same four
exhaustive matches in `app.rs` for one feature.

## Item 8 — currently reading

### 8a — engine (no migration)

`Storage::list_open_readings(limit) -> Vec<(Book, Reading)>`.

Build it as a variant of the join that already exists. `BOOK_FROM`
(`storage/books.rs:74-79`) resolves "the current reading" with a `LEFT JOIN`
whose subquery orders by `(finished_at IS NULL) DESC, COALESCE(started_at,
created_at) DESC`, and `BOOK_COLUMNS` projects `current_page` / `finished` /
`date_started` / `date_finished` off it.

> **Corrected during implementation (PR #5).** This section said to add
> `WHERE cur.finished_at IS NULL`. That is wrong, and wrong *silently*: the join
> is a `LEFT JOIN`, so a book with **no reading at all** produces a row whose
> every `cur` column is NULL — which satisfies `finished_at IS NULL`. The whole
> shelf comes back as "currently reading". The filter is
> **`WHERE cur.id IS NOT NULL AND cur.finished_at IS NULL`**.
>
> It was caught by writing the empty-library test first, which is the argument
> for writing that one first.

**Do not write a second join.** A separate query that disagreed with
`BOOK_COLUMNS` would make `Book`'s four projected fields inconsistent with the
home screen showing them, and the two would drift silently.

`Engine::currently_reading(limit)` on the facade. The TUI reaches into
`engine.storage` today, and that habit is what item 14 has to unpick; a new
feature should not add to it.

**`Engine` must be able to return a `NoteRecord` for a reflection.**
`open_reflection` returns `CreatedNote { id, title, file, links }`, but every
editor path in both frontends needs a `NoteRecord` — the CLI already patches
around it with a follow-up `storage.get_note(note.id)`
(`commands/reflect.rs:60-64`). 8b's whole action is "open the reflection", so it
meets this immediately. Add a record-returning wrapper over the existing
`open_anchored`; leave `open_reflection`'s signature alone, the CLI uses it.

Tests: a book with an open reading appears and a finished one does not; a reread
reopens and reappears; ordering is by most-recently-touched; the projected
fields agree with `Book`'s.

### 8b — TUI (absorbs item 7's deferred half)

New `Screen::Home`, and it becomes what the app opens to. `m` already returns to
the menu from anywhere, so the menu stays reachable and nothing becomes a dead
end.

- Rows are open readings, shrink-wrapped through the existing `list_box` and
  reusing `library.rs::progress_tag`. `Enter` opens the book; a key opens the
  reflection straight into the existing `TextEditor` (`ui/textedit.rs`).
- **No counts.** Rows are places you can go. "3 books need reflections" is
  forbidden by the axiom and is the easy thing to write here.
- The empty state is a place too: nothing open must show the way to library and
  search, not a blank pane. `Screen::Home` inherits the ambient layer for free
  (`ambient_visible()` is `motif != Off && screen != Book`), so its list box must
  `Clear` first like every other non-book screen.
- Reflection and review in the book view: **keys plus a kind marker in the Notes
  list**, not two new section tabs. `note_line` (`ui/book.rs:295`) already builds
  an `anchor_tag`, and `NoteRecord.kind` is loaded and never displayed. The
  section menu is about *collections of things*; a reflection is a singleton, and
  two tabs holding one item each is the wrong shape. A review's rating goes
  through the existing single-line `ui/input.rs`, validated by
  `RatingScale::canonical`.

The file-by-file cost of adding a screen, so it is not rediscovered: the `Screen`
enum and its `Action::Back` arm, the `MenuItem` enum and the `MENU` array whose
length is in its own type (`app.rs:48-100`), the `match app.screen` in
`ui::draw` (`ui/mod.rs:374`), the `match (self.screen, action)` in `App::handle`
(`app.rs:626`), and both test sweeps.

## Item 9 — backlinks

### 9a — engine + CLI · migration `0008`

```sql
CREATE INDEX idx_note_links_to     ON note_links(to_note);
CREATE INDEX idx_note_links_target ON note_links(target_title COLLATE NOCASE);
```

`note_links` has neither. A backlink query is a full scan today, and so is
`write_links`' back-resolution of dangling targets by title. Indexes only, no
shape change.

> **Corrected during implementation (PR #7).** This block originally wrote the
> second index without a collation. `write_links` back-resolves with
> `target_title = ? COLLATE NOCASE` (`storage/notes.rs:93`), and **SQLite will
> not use an index whose collation differs from the comparison's** — so a BINARY
> index leaves the plan at `SCAN note_links`, exactly as if the migration had not
> been written. Measured with `EXPLAIN QUERY PLAN`.
>
> An indexes-only migration can be judged on nothing except the plan the planner
> actually picks, which is why the thread asserts that plan before *and* after
> applying `0008` rather than asserting the index exists.

- `Storage::backlinks(note_id) -> Vec<NoteRecord>`, beside the existing outgoing
  `note_links(note_id)` (`storage/notes.rs:327`).
- `Engine::backlinks` and `Engine::outgoing_links`. The facade exposes **no** link
  method at all today — `note_links` is called only inside `open_anchored`.
- A test that back-resolution keeps `to_note` complete, so `backlinks` need not
  also union the dangling-by-title case. If it turns out it cannot, union it and
  say why in the doc comment.
- CLI `readingbuddy links <note>`, inbound and outbound, dangling targets marked
  as text. That is what makes the engine half reviewable without waiting for the
  pane.

### 9b — TUI · rebases onto 8b

The pane attaches to the **note list**, not a new tab: select a note in the Notes
section, a key shows what links in and out. Reuses the list machinery, adds no
`BookTab` variant, and puts the pane where the graph is actually consulted — on a
reflection, which is the hub.

## Item 10 — Goodreads CSV in and out · engine + CLI · migration `0009`

The largest of the three, and the one `docs/decisions.md` says "needs 3, 5, 7 to
import losslessly". All three are in.

### Migration `0009_goodreads.sql`

- `book_tags(book_id, tag, source, raw, PRIMARY KEY(book_id, tag, source))` —
  `Bookshelves` as **inert provenance**: raw value plus source, no UI, no merge
  semantics, until collections are designed. `docs/decisions.md` is explicit.
- `external_ids(source, external_id, book_id, PRIMARY KEY(source, external_id))`
  — Goodreads' own `Book Id`, and what makes re-importing the same CSV
  idempotent. General rather than a `goodreads_id` column, because Calibre
  (item 13) needs exactly the same table.
- `rating_scales.is_default`, back-filled to mark the current newest scale, with
  `active_rating_scale()` reading the flag.
- Seed a `goodreads` scale (min 0, max 5, step 1) with an identity `rating_map`.

**The `is_default` column is load-bearing, not tidying.** `active_rating_scale()`
is `ORDER BY created_at DESC, id DESC LIMIT 1` (`storage/ratings.rs:153-159`), so
inserting a `goodreads` scale makes it the active one — and `rb rating show` and
`set_rating` would silently start defaulting to it. Without the flag, item 10
changes the meaning of a command it has nothing to do with.

### Import

`Engine::import_goodreads(&Path, dry_run) -> GoodreadsReport`. Dependency
`csv = "1"` (Unlicense OR MIT; confirm with `cargo deny check licenses`).

- **`ISBN` and `ISBN13` arrive Excel-armoured**, as `="0316769487"`. Strip the
  armour, then through `normalize_isbn` like everything else — no exceptions,
  per `CLAUDE.md`.
- Matching: ISBN13 → ISBN10 → the existing `search.rs` jaro-winkler fingerprint.
  **Do not invent a second matcher.** Below the auto-match band, report unmatched
  *with candidates*, reusing `UnmatchedSidecar`'s vocabulary so unmatched is a
  decision rather than a dead end.
- `Exclusive Shelf` → `readings`. `read` → a finished reading; `currently-reading`
  → an open one; `to-read` → **a book with no reading at all**, which is the
  honest encoding and is why `to-read` needs no collection.
- `Read Count > 1` → that many readings, `source = 'goodreads'`. Only the most
  recent carries `Date Read`; the rest get NULL dates. Inventing dates for the
  earlier ones would be worse than admitting we do not have them — the same
  argument that leaves `reading_id` NULL on unattributable highlights.
- `My Review` → a note of `kind = 'review'` on that reading, respecting
  `idx_one_review`. `My Rating` (integer 0–5, 0 = unrated) → `review_ratings`
  against the **`goodreads` scale**, storing the raw integer. **Never reverse the
  `rating_map`** to guess a value on the user's own scale: the map is many-to-one,
  so the inverse is a guess, and decisions.md says store the raw value plus the
  scale id.
- `Private Notes` → a plain note titled for its origin. It is per-book prose that
  is neither a review nor a reflection, and folding it into either would put
  words in the user's reflection that they did not write there.

### Export

`Engine::export_goodreads() -> (String, Vec<Diagnostic>)`, mirroring
`export_flashcards`'s shape: return the payload, let the caller write it.

- Only the columns Goodreads' importer reads: `Title, Author, ISBN, My Rating,
  Date Read, Date Added, Bookshelves, Review`.
- `My Rating` through the existing `Engine::goodreads_rating`. On
  `EngineError::UnmappedRating`, **skip the row and emit a `Diagnostic` saying
  why** — the error's own doc comment says so, and a rounded star is exactly the
  failure the explicit lookup table exists to refuse.
- Rereads: Goodreads' CSV has no read-count column. Export the most recent
  reading and report the dropped ones as `Diagnostic`s. Silent truncation would
  look like data loss on the far side.

### Fixtures

`crates/corpus` gains `gen-goodreads` — still with no dependency on
`readingbuddy`, since the generator is an independent oracle.

Beside it, two or three **small hand-authored CSVs**, and the reason belongs in
their header: a Goodreads CSV is a *recorded artifact of another system*, like
the three KOReader checksums in `docs/koreader-format.md` §5. Generating one
from our own understanding of the format would prove only that we agree with
ourselves. They pin the shapes only a real export has — Excel-armoured ISBNs, an
empty rating beside a `0` rating, `Read Count 3`, a comma and a quote inside a
title, CRLF line endings, a book with no ISBN.

**The property worth having:** export → import → export is stable. It covers the
mapping table, the armour stripping and the reading reconstruction at once.

### CLI

`readingbuddy goodreads import <file> [--dry-run]` and
`goodreads export [-o file]`. `--dry-run` prints what would change and names the
flag that would do it — the same refusal-with-a-next-move shape as `ko sync`.

## Order, dependencies and threads

```
8a (currently-reading query) ──► 8b (home screen + reflection surface, TUI)
9a (backlinks, 0008)         ──► 9b (backlinks pane, TUI)
10 (Goodreads, 0009)  — independent of both
```

| Thread | Branch | Crates | Migration |
|---|---|---|---|
| T8a | `feat/engine-currently-reading` | engine | — |
| T9a | `feat/engine-backlinks` | engine, cli | `0008` |
| T10 | `feat/engine-goodreads` | engine, cli, corpus | `0009` |
| T8b | `feat/tui-home` | tui | — |
| T9b | `feat/tui-backlinks` | tui | — |

**Wave 1, in parallel: T8a, T9a, T10.** All three are engine-side, offline and
headless, which makes them the portable ones — they run in a cloud session with
nothing a sandbox lacks.

**Wave 2, one at a time: T8b, then T9b.** Not parallel, and the reason is
mechanical rather than stylistic: adding a screen touches four exhaustive
matches, the `MENU` array's length literal, and both test sweeps. Two worktrees
in a 2900-line `app.rs` is a conflict for no gain — the same call the 6b thread
made.

Both TUI threads are still cloud-viable. The suite is headless (`TestBackend`),
and `print_layout` / `print_lists` render composed layouts as ASCII with no tty,
which is how a thread shows what a layout change looks like. Only `make bench`,
`make bench-box` and `--probe` need a real, active pane.

### Rules for the parallel threads

1. **Migration numbers are pre-allocated — `0008` T9a, `0009` T10 — and merge in
   numeric order.** With the local database disposable, the old "out-of-order
   apply against a real `app.db`" hazard is gone; what remains is two branches
   minting the same filename, which
   `migration_versions_are_contiguous_from_one` now catches at PR time.
2. `Cargo.toml` is touched by T10 only (`csv`).
3. `crates/tui/**` is touched by T8b and T9b only; T9b rebases after T8b merges
   rather than resolving by hand.
4. Every thread runs the `cargo-tester` agent, then `make ci`, before its PR.
5. Nothing auto-merges. Each thread opens a PR, CI must be green, and the user
   reviews.
