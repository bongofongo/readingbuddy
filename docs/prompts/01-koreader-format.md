## 1a — investigation, no code

Produce `docs/koreader-format.md`. Three sources, in order of authority:

1. **KOReader's own source** — `frontend/apps/reader/modules/readerannotation.lua`,
   `frontend/docsettings.lua`,
   `frontend/apps/reader/modules/readerstatistics.lua`. This is the spec. Fetch
   it from the KOReader GitHub repo; do not rely on recollection of the format.
2. **Real sidecars you mint yourself.** KOReader ships desktop builds (Linux
   AppImage, macOS). Install one, run it against the epubs already in `epubs/`,
   make highlights, notes, a rating and a summary, close the book, and harvest
   the resulting `.sdr`. Put them in
   `crates/engine/tests/fixtures/koreader/real/` (gitignored). If you cannot get
   a desktop build running, say so plainly and fall back to source-reading —
   do not invent a fixture.
3. Ask the user for a device export if realism gaps remain.

**The blocking question, answer it first and state your evidence:**

> Does editing an annotation's note in KOReader change that annotation's
> `datetime`?

It decides everything downstream:

- **No** → our identity hash is stable across a note edit, the edit is currently
  dropped silently, and item 2's targeted-update fix is correct as designed.
- **Yes** → the hash changes and **the same highlight re-imports as a duplicate
  row**. No conflict handling fixes that. The identity hash would have to drop
  `ko_datetime` and key on `pos0` + `text`. **Stop and report to the user before
  writing any code** — item 2 needs re-planning.

Also document: the exact shape of `summary` (field names, the `status` value
set, the rating's range and type, whether its `note` is the user's review);
`percent_finished`'s type and range; the `stats` subtable's fields and whether
its `md5` is the same value as the root `partial_md5_checksum`; the
`util.partialMD5` algorithm (for later, not this item); and whether the legacy
pre-`annotations` format carries any of it.

## 1b — parse and expose

Extend `KoSidecar` (`crates/engine/src/koreader.rs:34`) with
`percent_finished`, `summary` and `stats` per your findings. `status` is a typed
enum with an `Other(String)` fallback — an unknown status from a future KOReader
must degrade, never fail an import.

**Note before you plan storage:** `partial_md5` is *already parsed* from the
root `partial_md5_checksum` key (`koreader.rs:78`) and then never used. It does
not need computing.

Add migration `0003_device_books.sql` exactly as specified in the spec, and give
`match_book` a new first branch — `partial_md5` → `device_books` → `book_id`,
ahead of the sibling-epub ISBN lookup. `MatchMethod` gains `Md5`.

**Persist `partial_md5` only.** Rating, status and `percent_finished` are
carried in the parse result and the report but have nowhere correct to live
until the `readings` table exists (build item 4). **Do not park them on `books`**
— that column set is about to move.

## Fixtures

Generated by `crates/corpus/src/synthetic.rs` (`make synthetic`), never
hand-written — the generator must not depend on `readingbuddy`, or a parser bug
gets baked into the goldens. Four new cases, each with a golden: `Summary.sdr`,
`Stats.sdr`, `SummaryLegacy.sdr`, `SummaryUnknownStatus.sdr`.

## Constraints

- Engine only. No TUI, no CLI beyond whatever the import output already prints.
- No network in tests, ever.
- No silently-skipping tests — every skip prints `SKIPPED:` and honours
  `READINGBUDDY_REQUIRE_FIXTURES=1`.
- Typed `Diagnostic`s, never pre-formatted strings.
- Never edit an applied migration; add a new numbered one.
- Highlight text, note bodies and search queries never go above `trace!`.

## Done when

`docs/koreader-format.md` answers the `datetime` question with evidence; the
four fixtures and goldens are committed; `partial_md5` matching works end to
end; `make ci` is green. Run the `cargo-tester` agent before committing.
