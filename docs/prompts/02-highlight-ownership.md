## The problem

`identity_hash = sha256(book_id | ko_datetime | pos0 | text)`
(`crates/engine/src/storage/highlights.rs:22`) — `note` and `color` are payload,
not identity. That's correct: if `note` were in the hash, typing a note on the
device would import a *second copy* of the highlight.

But the insert is `ON CONFLICT(book_id, identity_hash) DO NOTHING`
(`highlights.rs:55`), so **a note edited on the device is silently discarded on
re-import**. It reports as `skipped`, indistinguishable from "already had it,
identical".

That contradicts the project's ownership rule: KOReader is the *origin* of
`note` and `color`, so the device wins on refresh.

## The work

**Migration `0004_highlight_ownership.sql`:** rename `highlights.note` →
`ko_note` (theirs), add `annotation` (ours, never touched by import), add
`last_seen_ko_note`. The last is unused today and exists so a future two-way
sync can distinguish "the user changed it here" from "the device changed it
there" — unrecoverable if only the merged result is ever stored.

**Leave `insert_highlight` exactly as it is.** Do not turn `DO NOTHING` into
`DO UPDATE`: `RETURNING id` would then yield a row on the conflict path too, so
`Some(id)` stops meaning "newly inserted" and the `inserted`/`skipped` counts
the goldens assert collapse into each other.

Add `refresh_device_fields(book_id, &NewHighlight) -> Result<bool>` instead,
called when the insert returns `None`. It updates `ko_note`, `color`, `chapter`,
`page` and sets `last_seen_ko_note`; it must compare before writing so the
boolean (and therefore the counter) is accurate; it must never touch
`annotation`, `source`, `created_at` or `id`.

**Use straight assignment, not `COALESCE`.** The books upsert's
`COALESCE(excluded.x, books.x)` no-clobber pattern is right for *providers* —
they return partial records, so a missing field means "I don't know". A sidecar
is the *complete* state of that annotation, so a missing note means the user
**deleted** it. Copying the books pattern here would make note deletion
impossible to sync, permanently.

**`BookImportStats` gains `updated: usize`**; `skipped` narrows to "present and
identical". Surface the count in CLI import output.

## Fixture

`variants/Pachinko-NoteEdited.sdr`, generated by
`crates/corpus/src/synthetic.rs` — byte-identical to `Pachinko.sdr` except one
existing annotation's note text. Sibling to the existing
`variants/Pachinko-Superset.sdr`, and for the same recorded reason: **a
committed fixture, not a string splice.**

## Tests — the invariant splits three ways

`reimport_is_strictly_idempotent`
(`crates/engine/tests/koreader_import.rs:300`) is **not wrong and stays
unchanged.** It re-imports an identical fixture, and identical bytes genuinely
should change nothing. What it cannot do is distinguish "nothing should have
changed" from "we discard device updates" — that fixture contains no device
update. The gap is a missing fixture, not a too-strong assertion.

Add two:

- `device_edits_refresh_but_ours_survive` — import `Pachinko.sdr`, set an
  `annotation` on the highlight that's about to change, import
  `Pachinko-NoteEdited.sdr`. Assert `inserted == 0`, `updated == 1`, `ko_note`
  is the new value, and `annotation` / `created_at` / `source` are untouched.
- `highlight_ids_are_stable_across_refresh` — capture ids before, assert
  identical after. **This is the one that would really hurt:**
  `notes.highlight_id` and `flashcards.highlight_id` are foreign keys
  (`0001_init.sql:48`, `:67`), so a delete-and-reinsert refresh would silently
  null note anchors and cascade flashcards away.

Then `make synthetic` and `make golden`. **Review the golden diff** — the
`updated` counter should be the only semantic change. Anything else is a bug.
