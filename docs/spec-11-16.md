# Roadmap: items 11–16

Items 1–10 are on `main` (`79c9f1d`), migrations `0001`–`0009`. This is the rest
of `docs/decisions.md`'s build order.

**This is a roadmap, not five thread prompts.** Items 8–10 were specified in
full and four of the five threads still found an error in the spec — three of
which would have shipped green. Specifying items 14 and 15 in that detail now,
against a codebase two waves away from existing, would produce more of the same
and cost more to unpick. So: 11, 12 and 13 are specified to the point where a
thread prompt is a mechanical translation; 14 and 15 get the constraints that are
already known and decided, and are re-planned when reached. Write the prompt for
a wave when you launch it, as items 4–7 and 8–10 both did.

Everything is held to the **Engine standards** section of `CLAUDE.md`.

## What this wave inherits

Worth stating, because three of these change what the items below cost:

- **The gate is real.** ubuntu runs `--workspace --locked`, so a TUI or CLI break
  shows on the PR. `make ci` reproduces it.
- **Migration numbering is mechanised** — a contiguity test plus a PR job
  refusing an edited migration. Pre-allocate numbers across parallel threads and
  merge in numeric order; the guards catch a collision at PR time.
- **`external_ids(source, external_id, book_id)` already exists** (migration
  `0009`). It was made general rather than a `goodreads_id` column *because*
  Calibre needs the same table — item 13 gets it for free.
- **`partial_md5` exists** and `import_epub` already records `device_books`,
  which is dedup level 3's middle rung.
- **`is_koreader_mount` exists** and knows all three install layouts, requiring
  `reader.lua` + `frontend/` + `plugins/`. It was built to be the gate that
  refuses to write a plugin onto an unrecognised volume — item 15's safety
  predicate, settled while it was still read-only.
- **Narrative workflow tests** (`crates/engine/tests/workflows.rs`) and **CLI
  subprocess tests** (`crates/cli/tests/cli.rs`) exist. New cross-item stories go
  in the first; the second has a golden of the subcommand name set that any new
  command must update.

## Item 11 — wired device watcher

Mount → scan → import with nothing typed. `docs/decisions.md` says macOS
`/Volumes/…`, Linux `/run/media/$USER/…` and `/media/$USER/…` — all three already
in `device::candidate_mounts`.

**The whole engine surface already exists.** `scan_device`, `sync_device`,
`candidate_mounts`, `is_koreader_mount`, and the `sidecar_seen` cache that makes
a rescan cost nothing. What is missing is *noticing* a mount without being asked.

- Dependency `notify` (or `notify-debouncer-full`). Check `deny.toml` first.
- **The engine half must take an injectable event source**, not a `notify`
  watcher hard-wired into it. That is the only way this is testable at all: a
  test feeds mount/unmount events and asserts the debounce, the ordering and
  that a scan is not started twice for one mount. A watcher that can only be
  driven by plugging in real hardware is a watcher with no tests.
- **Debounce is the substance.** A mount appears as a burst of filesystem events
  and a device that is still writing will produce a sidecar mid-flush. The scan
  must not start on the first event.
- **Read-only on arrival, always.** `docs/decisions.md` is explicit: mount →
  import is automatic and read-only; anything that *writes* to the device is
  explicit and shows the path. The watcher may scan; it may not sync.
- TUI: the device screen exists (item 6b). A mount arriving while it is open
  should refresh it through the existing `pending_scan` deferred-work path — one
  unit per loop iteration, drained after the redraw. Do **not** widen
  `animating()`.
- Verification: the engine half in CI with a fake source; the real thing needs
  hardware and is local-only. Say which was which.

## Item 12 — `book_files`, owned files, three-level dedup

Engine-only, offline, deterministic — the most cloud-friendly item left.

Migration **`0010_book_files.sql`**:

```sql
book_files(book_id, sha256, format, original_name, size)
```

Content-addressed storage at `database/files/<ab>/<sha256>.<ext>`; the original
filename is a **column, not the path**. `EngineConfig` gains `files_dir` beside
`images_dir` and `vault_dir`, and `Engine::open` creates it.

**The three dedup levels are distinct and conflating them is the usual mistake**
(`docs/decisions.md` names it):

1. same bytes → **sha256**
2. same book, different file → **many-to-one via `book_id`** (epub + azw3 = two
   files, one book)
3. same book, unknown → ISBN → **`partial_md5`** → the existing `search.rs`
   jaro-winkler fingerprint

**Do not invent a second matcher for level 3.** Every rung already exists;
`koreader::title_scores_for` was already split out for item 10's reuse.

Two things to get right:

- **sha256 is the content address; `partial_md5` is not.** It samples twelve
  1024-byte windows, so two files identical at those windows collide. Fine for
  dedup, sidecar↔book matching and the `statistics.sqlite3` join; wrong here.
  `partial_md5.rs`'s module doc already says so.
- **Import must be crash-safe.** Write to a temp path in the same directory and
  rename into place, or a killed import leaves a half-file at a name that claims
  to be its own hash.

`merge_books` must repoint `book_files`, like it now does for `book_tags` and
`external_ids`. That is not housekeeping: they cascade on `books`, so leaving
them deletes them with `src`.

## Item 13 — Calibre, tiers (i) and (ii)

**Feature-detected, never a hard dependency.** Present → the features work;
absent → they are not there. Never ask the user to install or configure it.
Shelling out to a GPL-3 binary is **not linking**, so no licence contamination —
unlike the in-process `epub =2.1.4`.

- **(i) `ebook-convert`** — format conversion. The tier `docs/decisions.md` puts
  first.
- **(ii) `calibredb list --for-machine`** — library import. JSON out, so no
  scraping. Books land through the existing matcher and record
  `external_ids(source = 'calibre', …)` — **the table item 10 already built for
  exactly this**.

Testable in CI without Calibre: put a **fake `ebook-convert` / `calibredb` on
`PATH`** (a script in a tempdir) and assert the command line built, the JSON
parsed, and the absent-binary path. `crates/cli/tests/cli.rs` already
demonstrates the environment-pinning discipline that needs. Confirm against a
real install locally and say so.

Feature detection must be **cached per run, not per call** — probing `PATH` once
per book on a library import is a syscall per book for an answer that cannot
change mid-run.

## Item 14 — the API crate and `readingbuddyd`

**The boundary is the API, not the process.** A versioned API crate holds the
whole surface; the daemon is a thin transport wrapper with no logic. That is what
keeps iOS — which has no daemons — able to link the same crate in-process.

**The real cost is not the transport.** It is the seam, and it is measurable
today:

- **No serde on any domain type.** `Book`, `NoteRecord`, `Highlight`, `Reading`,
  `DeviceBook`, `Rating`, `MergeReport`, `CreatedNote` are all `Debug, Clone`
  and nothing more. `serde` is a dependency but is used only for the
  `books.authors` JSON column and provider response parsing.
- **Non-serializable types cross the facade**: `PathBuf` in and out,
  `OffsetDateTime` on `Book`, `&mut Book` in `download_cover`, `&mut self` in
  `set_google_api_key`, and `EngineError` wraps `sqlx::Error` / `reqwest::Error`
  / `io::Error`.
- **`Engine::storage` and `Engine::config` are public fields** and both frontends
  reach past the facade through them. Readings, ratings-scale admin and highlight
  listing have no `Engine` method at all. Item 8a and 8b both had to be told not
  to add to this habit.

So the item is: DTOs with `From<domain>`, a facade complete enough that
`pub storage` can go private, and a stable error taxonomy — *then* a transport.
`Diagnostic`/`DiagnosticKind`/`ErrorClass` are already `Clone` + frontend-shaped
and are the closest thing to a DTO layer that exists; use them as the pattern.

Do this **after** items 11–13, not before: each of them adds facade surface, and
freezing an API around a facade that is about to grow three more subsystems is
the version of this that has to be done twice.

## Item 15 — the KOReader plugin and wireless push

Plugin lives **on the reader** (`koreader/plugins/readingbuddy.koplugin/`, Lua).
readingbuddy installs it itself over the wired path, reversibly — never by asking
for a config edit.

Safety, and `docs/decisions.md` calls it non-negotiable:

- verify the mount is really a KOReader install — **`is_koreader_mount` is that
  gate and already exists**;
- write only inside our own plugin directory;
- create-only; an upgrade replaces only our directory; refuse to overwrite a
  newer version;
- **never automatic** — mount → import is automatic and read-only, mount →
  install is explicit and shows the path;
- uninstall is exact;
- the plugin **fails closed** and never blocks or slows the reader UI.

The installer's predicates and the refusal paths are cloud-testable against a
fake mount tree. The plugin itself needs hardware.

**Slice a — the installer and the pairing — is done.** See `docs/decisions.md`
entry 15 for what building it changed; `docs/prompts/15a-the-plugin-and-the-pairing.md`
is the prompt it was built from. Three corrections to the paragraphs above:

- **"The plugin itself needs hardware" was too strong**, and it is what deferred
  the item for a wave. KOReader ships a desktop build running the same plugin
  loader, and `datastorage.lua:20` reads `KO_HOME` before every other branch —
  so `KO_HOME=/tmp/ko-test` gives the Lua an edit loop with no device in it.
  What needs hardware is confirming the three mount layouts and FAT32's
  behaviour, which is a smaller claim.
- **The install target is durable and that is now a checked fact**, not an
  assumption: a KOReader OTA update is a tar unpack with no `--delete` whose
  only removal is a manifest diff, so a directory that never appeared in a
  KOReader manifest survives.
- **"Wireless push" is slice b and shares none of this code.** What slice a
  leaves it is a paired reader with a token and no endpoint, so 15b's first
  question is the listener — and `crates/daemon` is unix-socket-only by a
  written argument (`server.rs:9-21`) that item 15 is precisely the case for
  overturning.

## Item 16 — the bucket

Everything under *Out of scope for now* in `docs/decisions.md`, plus collections,
the Tauri GUI and the Mac/iOS companions. Two entries have acquired constraints
worth recording before they are planned:

- **Collections.** Deferred because three systems minting them is a merge problem
  with no good default. `book_tags` now holds **real Goodreads shelf data as
  inert provenance** — raw value plus source, nothing reading it — so this design
  can finally be made against the shelf names the user actually typed rather than
  against a guess.
- **Excerpt view.** When it lands: **search the epub for the highlight's text**,
  not `pos0` resolution. A `pos0` is a cre-engine xpointer and resolving it means
  reimplementing enough of that engine to agree with it.

## Suggested order and shape

```
11 (watcher)   engine + tui   — needs hardware to confirm
12 (files)     engine         — migration 0010, offline, parallel-safe
13 (calibre)   engine + cli   — feature-detected, fake-binary tests
      ↓
14 (api + daemon)              — after 11-13, or it is done twice
15 (plugin)                    — needs hardware
16 (bucket)
```

**11, 12 and 13 can run in parallel.** They share no files: the watcher is
`device.rs` plus a TUI hook, files is a new module plus `merge_books`, Calibre is
a new module plus CLI. Only item 12 takes a migration (`0010`).

Rules that carried this wave and should carry the next: pre-allocate migration
numbers and merge in numeric order; one PR per thread, green CI, human review,
nothing auto-merges; and tell each thread to **push back rather than comply** —
four of five did, and each time they were right.
