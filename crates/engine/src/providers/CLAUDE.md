# providers/, search.rs, matching.rs

Metadata providers, the federated search over them, and the one matcher every
"is this the book I already have" path shares. Moved here from the root
`CLAUDE.md` unchanged.

`matching.rs` lives at `crates/engine/src/matching.rs`, not in this directory —
it is documented here because it is the other half of the same question.

Siblings: [`../storage/CLAUDE.md`](../storage/CLAUDE.md) ·
[`../../CLAUDE.md`](../../CLAUDE.md) (crate rules)

- `providers/` — `MetadataProvider` trait (`async_trait`, boxed): `openlibrary.rs` (search.json + /isbn/{}.json edition lookup with concurrent author-key resolution), `googlebooks.rs` (volumes?q= with `intitle:/inauthor:/inpublisher:`; API key optional via `GOOGLE_BOOKS_API_KEY`, keyless 429s degrade to warnings). Language codes normalized MARC↔BCP-47 in `providers/mod.rs`.
- `search.rs` — federated fan-out (5s per-provider timeout, failures become warnings), dedup (canonical ISBN-13 key, else fuzzy title+author fingerprint, jaro-winkler), field-wise merge (OL wins isbn/pages, GB wins description/language), pure `rank()` (exact ISBN 1000 ≫ title 40 > author 25 > publisher 10...).
- **`matching.rs` — "is this the book I already have", once.** The one rule behind every path that meets a book from somewhere else: a sidecar, a Goodreads row, a calibre row, an owned file. `Prepared::new(&Query { title, authors })` is built once per scan and `compare`d against every library book; `koreader::scores_for` is the storage half and `koreader::band` filters what is left into candidates. **It used to be a bare `jaro_winkler` on the two titles, and that was the bug**: JW is a character-transposition metric with a four-character prefix bonus built for *personal names*, `search::normalize` drops a leading article (which makes a shared first word, and therefore that bonus, *more* likely), and `0.60` is not a weak threshold for it — for two English titles it is roughly "both are English". Measured over 780 pairs of real titles, **10% landed in the 0.60–0.85 band**, and the band is reported as the **maximum over the whole library**, so it is an extreme-value draw: at fifty books the chance something scores into it is 99.5%. Every unmatched row therefore grew a confident wrong candidate (`Pachinko`/`Pinocchio` 72%, `The Left Hand of Darkness`/`The Lathe of Heaven` 71%) and `Dune`/`Dune Messiah` at 87% **linked itself to the wrong book**. Two signals fix it. **The titles must share a content word** — `score = 0.65·jaro_winkler + 0.35·dice` over stopword-stripped tokens, and no shared token at all is `None` (not a low score) unless the raw strings are above `TYPO_ONLY` = 0.90, which is a misspelled one-word title rather than a coincidence. **The authors must not disagree** — a **veto only**, at `AUTHOR_DROP` = 0.55, and deliberately that low because no threshold separates `J.R.R. Tolkien` from `John Ronald Reuel Tolkien` (one person, 0.65) without also merging `Frank Herbert` with `Brian Herbert` (two, 0.90); asked to decide that the signal would be wrong either way, so it is not asked. Absence is **not** disagreement: either side having no author leans on the title alone, which is the common case (a sidecar-seeded book, a file matched by its stem). `author_key` compares **alphabetically sorted tokens**, because calibre says `Min Jin Lee` and an epub's `author_sort` says `Lee, Min Jin` and those two score like different people as written. `compare` returning `None` is the half that matters — the old matcher had no way to say *nothing here looks like it*, so it always named its best coincidence.
- **Subjects and series (item 32, migration `0013`).** `normalize_subjects` in `providers/mod.rs` is **shape only, never vocabulary**: trim, drop empties, dedup case-insensitively keeping the first spelling. The strings stay as published, because mapping Google's BISAC paths onto OpenLibrary's headings *is* a controlled vocabulary and that is the question `book_tags` deferred — not one answerable from two examples. There is deliberately **no cap** either: OpenLibrary works genuinely carry a hundred subjects, many of them cataloguing artifacts (`Accessible book`, `Protected DAISY`, `In library`), and a silent truncation is indistinguishable from a short list, while filtering the artifacts is the same vocabulary decision. Both are left for a design made against real data — which is exactly what storing them raw makes possible. **Google Books**: `volumeInfo.categories`, free, in the response already there. **No series from Google** — `volumeInfo` has no documented series field, and the `seriesInfo` block some volumes carry is absent from the API reference, so the only possible fixture is one written from memory, which would prove that we agree with ourselves and nothing else (the argument `fixtures/goodreads/README.md` makes for keeping recorded samples recorded). **OpenLibrary**: series comes off the *edition* (`series: ["Dune Chronicles #2"]`, free text), and `split_series` reads **a trailing `#N` or `; N` and nothing else** — `Bd. 3 : Der Zauberberg` keeps its whole string as the name, because a wrong `#2` is a confident claim about *which book this is* and the pair guard can only help with a missing value, never a wrong one. Subjects live on the **work**, never the edition, so they cost **one extra request per book looked up**: `by_isbn` goes from 1 + *authors* requests to 2 + *authors*, issued concurrently with the author resolution so it is a request rather than a round trip. `search.json` deliberately does **not** ask for its `subject` facet — that would enlarge every response of every search by the noisiest form of the field, for data only a saved book has a use for. A failed `/works/` fetch **degrades to no subjects** rather than failing the lookup: the edition already answered the question that was asked, unlike the author resolution beside it, whose result is part of identity.
