- `storage/` — concrete `Storage` struct over `SqlitePool`. This struct is the deliberate swap boundary (no trait until a second backend exists). `sqlx::migrate!` runs `crates/engine/migrations/` on connect; foreign keys ON per connection. Upserts keep the isbn_10 → isbn_13 → neither `ON CONFLICT` branching with `COALESCE(excluded.x, books.x)` no-clobber merging.
  - **Pages, filters and counts (item 18, `storage/query.rs`, no migration).** `list_books` takes one `BookQuery` — sort, filter, limit, offset — and `count_books` takes the filter half of it. **The two share one `WHERE`, written by `BookFilter::predicate` and by nothing else**, because two hand-written clauses that agree today disagree the first time a filter is added to one of them; `the_count_agrees_with_the_page_for_every_filter` sweeps ten filters against all five sorts. **Pagination is an offset in every arm** and the argument is in `docs/decisions.md` entry 18: two of five sorts (`Progress`, a computed ratio across a LEFT JOIN; `Author`, not an `ORDER BY` at all) have no cursor key that exists in the database, and they are exactly the two whose pages are already whole-table reads, so keyset would cost a second pagination shape at every call site to speed up only the sorts that were already cheap. **Every SQL arm ends in `books.id`**, which offset paging needs and the spec did not mention — and the tie-break's absence is *not* catchable behaviourally: removing it leaves `a_page_and_its_successor_partition_the_list` green, because SQLite's sorter is deterministic for one plan over one set of rows. That determinism belongs to the query plan and not to the schema, so the guard is `order_by_is_a_total_order`, which reads the SQL. Keep it structural. **`StatusFilter::NoReading` is `cur.id IS NULL`** — the join's absence, deliberately not `cur.status IS NULL`, since a reading with a null status is a book that *has* been opened — and it lives on the filter rather than as a `ReadingState::NeverOpened`, which is the banned completion framing wearing a type. **A negative limit is no limit**, honoured identically by the SQL arm and by `list_books_by_author`'s Rust slice, so the two cannot mean different things by the same number; `BookQuery::default()` is the honest spelling of the whole-library read that `koreader::scores_for` and `goodreads::export` used to write as `10_000` and `i64::MAX`. **`book_summaries(&[id])` is three grouped aggregates for a whole page**, one row per id in the order asked with zeros included — counts rather than marks, because at this shape the boolean is not the cheaper query and `BookSummary::has` is the mark. **`list_notes` gained an `Option<i64>` limit and kept `None`**: `resolve_note` walks every title in the vault, and a default cap would silently truncate a correctness pass.
  - **Field provenance (migration `0012`, `storage/field_provenance.rs`).** `docs/decisions.md`'s "Authority is per-field. Provenance is recorded." — the second sentence, which was not true: `external_ids`/`book_tags` record provenance about **rows**, and nothing said where `page_count` came from. One row per `(book_id, field)` holding `source` + `fetched_at`, vocabulary in a comment rather than a `CHECK` (the `readings.source` precedent from `0005`). **Its own module, not a section of `provenance.rs`**, whose defining property is being *inert*: this table is read by the merge SQL on every write to `books`, and a `user` row changes what that write does. **`user` outranks everything** — a field the user owns is not overwritten, and the rule lives in the generated SQL (`merge_set`'s `guard_user`, from the one predicate `field_provenance::user_owns`) rather than in each caller, because item 30 is a new caller and a caller-side rule is a rule that has to be remembered once per writer. `guards_user` is the one statement of "everyone except the user themself"; an *unattributed* write is guarded like any other, since not knowing who is writing is not a reason to let them past a correction. **Written from `MERGE_RULES`, never beside it**: that table gained a `says: fn(&Book) -> bool` per column and now generates four things — the upsert's `ON CONFLICT`, `enrich_book`'s `UPDATE`, `merge_books`'s `dst`-wins fill (which used to be sixteen hand-written columns, i.e. exactly the second list item 32 would have had to remember) and the set of fields each of them stamps. `a_record_claims_exactly_the_fields_it_supplies` sweeps every rule and asserts that a record speaking to one column moves that column and claims that field — a wrong `says` shows up as a missing claim, a wrong bind order as the *neighbouring* column moving. **Provenance travels with the value, not the row**: `merge_books` moves `src`'s claims only for fields `dst` was silent about, because `dst` wins the fill and a field `dst` holds *unattributed* must stay unattributed rather than inherit the claim on a discarded value. **Not every writer can attribute, and the ones that cannot say nothing**: `save_book` holds a record already flattened by `search::merge_provider_books`, which keeps the winning value and throws away which provider supplied it, so it stamps `None` — item 30 merges provider by provider and is where that becomes answerable. `import_epub` *could* not attribute either until it was split into two writes, which is why `fill_book` exists (the mirror of `enrich_book`: the stored row wins, the incoming record fills gaps, and claims only what it filled) — the file's metadata was previously folded onto the provider's with a hand-written `is_none()` per column, which is `MERGE_RULES` spelled a second time *and* one row with two origins that no single stamp could describe. **No `value_hash`** and **no back-fill**; both are argued in the migration and the module header.
    - **Item 30 added the fifth thing the table generates and the write that uses it.** `Rule::show: fn(&Book) -> Option<String>` is the `Book`-to-text projection `EnrichReport` needs to name the value a provider *offered* for a field it was not allowed to write — reported by name alone, a held-back field is exactly the "silently not updated" state the report exists to remove — and it lives in the table because a projection written beside it is the second column list all of this is arranged to make unrepresentable. `show_and_says_agree_on_every_column` sweeps `PROBES` and pins that `show` is `Some` exactly when `says` is true: they are two readings of one question, and a column where they disagree is either claimed and unprintable or printable and unclaimed. `Storage::enrich_book_attributed(id, book, &[(field, Source)])` is the multi-source write — **one statement, per-field stamps**, because the alternative (one `enrich_book` per provider) attributes honestly and loses `search`'s tuned per-field preference, whichever provider ran first winning every field it spoke to. `enrich_book` is now a thin wrapper over it, so there is still one statement and one guard: `guard_user` is `claims.iter().all(guards_user)`, which is the single-source rule reached through the same predicate rather than re-spelled, and a mixed set containing `Source::User` guards like any other — the safe direction, and not a set any caller produces.
  - **Subjects, series and the pair a claim cannot protect (item 32, migration `0013`).** Three columns on `books`, which is three `MERGE_RULES` rows and *nothing else* — the arrangement item 29 built paid off exactly here, and the sweeps caught the one place it did not: `every_claimed_field_is_a_merge_column` failed with "subjects was supplied but never claimed" the moment the column existed, because `search::merge_into` is the fourth consumer and — **until the surfacing item that followed** — was not generated. It is now: `Rule::federated` is the sixth thing the table produces, carrying how a column merges when *two providers* meet (fill, or a per-column `Prefer(Source)`, or `WithPair` for an index that never moves without its name) plus the setter that does it. `Federated::Local` is the only way out and names exactly two columns, asserted by `only_our_own_columns_sit_out_the_federated_merge`, so "make it Local" cannot be the quiet way to skip the question. The merge body lives in `books.rs` as `merge_provider_record`; `search::merge_into` is now the `FieldClaims` bookkeeping alone. **`subjects` is a JSON array with `Merge::NonEmptyList`**, the rule `authors` already had, and that is the answer to "`MERGE_RULES` has no vocabulary for a set": it did, under another name. A provider with subjects replaces the stored set whole and `[]` means *this record does not say*. **Not a union**, and that is the decision: Google's `categories` are BISAC paths and OpenLibrary's work `subjects` are free-text headings, so a union is a two-dialect pile no source published — and `field_provenance` holds one `source` per field, so it would have to name one of two origins for a value that came from both. Union is unrepresentable in this schema, not merely undesirable. Subjects are emphatically **not `book_tags`**: those are minted shelves and `docs/decisions.md` defers collections; a provider subject is a bibliographic fact with an origin, like a publisher. **`series` + `series_index` is a pair**, and per-field provenance cannot protect one — item 30 recorded exactly this bug for `isbn_13`/`isbn_10` (a user-owned 13 held while the 10 landed from a different edition) and left it because the fix looked like it needed a claim with no value. It does not: **`Rule::pair` guards both halves off either half's claim**, which is strictly weaker and enough for both instances, because in both the incoherence is only ever introduced by a write to the *unowned* half. So the ISBN case takes the same guard and is fixed here. The guard has to be in **two** places from one rule — `merge_set`'s SQL *and* the stamp, via `claimable`/`user_owns_now` — because a paired column held by its partner's claim has no `user` row of its own, so `stamp`'s own `WHERE` (which only protects the same field) would claim it for a provider whose value the merge had just refused: a value held and a claim granted is the half-protected field the guard exists to prevent, and the test caught it on the first run. `pairs_are_symmetric` pins the other half of that — a pairing that only goes one way guards the one direction that was never at risk. `series_index` is **REAL**: novellas are 0.5 everywhere, and `Rule::show` prints `#2` rather than `2` because a REAL column renders whole numbers as `2` in every report otherwise. **The TOC is deliberately not here** — see "epub.rs" in [`../../CLAUDE.md`](../../CLAUDE.md) for why a chapter list is derived rather than a fourth column.
  - **Cover metrics, and the columns that are deliberately *not* merge rows (item 20, migration `0014`).** Four columns on `books` — `cover_width`, `cover_height`, `cover_accent`, `cover_thumb_path` — and the decision worth carrying is that **none of them is a `MERGE_RULES` row**, which is the opposite of what `0013` did with three columns and is the first time that has been the right answer. `MERGE_RULES` governs what a *record* can carry, with a source to attribute; no provider publishes a width, and the only honest answer to "where did this come from" is "we decoded the file". A `Federated::Local` row would say that in the table's vocabulary and would then hand every record-shaped writer (`upsert_book`, `enrich_book`, `fill_book`, `set_book_fields`) a way to move one of them *without* moving `cover_path` — a row whose stored dimensions describe a different image, which nothing downstream can tell from a correct one. **`Rule::pair` is not the fix**, for three separate reasons: it is binary and asserted symmetric where this is a star of four columns around a fifth; it guards against a *user claim* rather than against incoherence; and `merge_books`' fill — the one place the incoherence was genuinely reachable — runs with the user guard **off**, so the pair guard would never have fired there at all. So they take reading state's shape instead: **`Storage::set_cover` is their only writer**, assigning all five columns beside the path they describe, and `a_provider_write_never_touches_the_cover_metrics` pins the absence the way `a_provider_upsert_never_touches_reading_state` does. **One writer was not enough and the test said so**: `cover_path` *is* a merge column with three other writers, and `Merge::Coalesce` under `Winner::Incoming` means an incoming record's path wins, so a calibre row or an `rb set` carrying a cover repointed the row and left the previous jacket's measurements behind it. `merge_set` therefore generates a seventh thing — `invalidate_cover_metrics` — which sets the four back to NULL whenever the path moves, **from the same expression that stores the path**, so it cannot fall out of step with the merge rule, the user guard or the `dst`-wins inversion. `merge_books` carries them explicitly in the one case its fill moves the path (`dst` had none, `src` did); nothing is written when `dst` kept its own jacket, since `src`'s numbers are about a file `dst` is not using. **`set_cover` replaces where every other writer coalesces**, which fixed a latent bug rather than adding an exception: `download_cover` went through the no-clobber merge, so a re-fetch producing a *different* file left the row on the old one — invisible under URL naming, where the new file usually had the same name. Its `source` claims **`cover_path` and nothing else**: the file has an origin (whoever supplied the URL), the measurements do not. Two more consequences of content-addressed names live in this file: `delete_book` and `merge_books` return a cover path to unlink only when **no other row references it**, because two books that fetched the same jacket now genuinely share one file — `book_files` gets to skip that check since it is keyed on the sha alone and a second holder is unrepresentable there, and `books` holds a plain column where a second holder is ordinary. `Storage::unmeasured_covers` states the back-fill's work list once (`cover_path IS NOT NULL AND cover_width IS NULL`, which is *not measured yet* and never *no cover*).
  - **One search surface (item 34, migration `0015`, `storage/fts.rs`).** `notes_fts` was the only virtual table in the repo, so a search box found the six notes a reader had written and none of the four hundred passages they kept. `highlights_fts` is **external content over `highlights`, maintained by three triggers**, and the argument for triggers is the exact inverse of the one that keeps `notes_fts` free of them: a note's body is *not in the database*, so a trigger has nothing to read, while `highlights.text` is a column — and external content means the reader's private passages are not written a second time. What it buys is that **no write path can skip the index**: `insert_highlight`, `refresh_device_fields`, `set_annotation`, `merge_books`' drop and `delete_book`'s cascade all maintain it without naming it, and so does `crates/corpus`' `gen-devdb`, which writes raw SQL and by design does not link the engine — an explicit Rust writer would have had to be re-implemented there, exactly as `notes_fts` in fact is. Two things in the migration were **measured against sqlite3 3.51, not reasoned about**: a foreign-key cascade *does* fire the delete trigger (without it a deleted book's rowids keep coming back from `MATCH`), and the update trigger is `AFTER UPDATE OF text, ko_note, annotation`, because `attribute_highlights` rewrites `reading_id` for every highlight of a book on every import and `merge_books` rewrites `book_id` per moved row — neither touches an indexed column. `chapter` is deliberately unindexed: every highlight in a book carries one, so it matches broadly and means nothing. **`Storage::search_marks` is the one reader of both indexes** and returns **one ordered list**, because two lists a frontend interleaves is a relevance ordering invented above the seam. It is **not ordered by bm25 across the two**: fts5's rank comes from that index's own corpus, so a note's −8.2 and a highlight's −8.2 are not the same claim and no constant converts one into the other. Each index is ordered by its own rank and the two are merged **by within-source position** (reciprocal rank fusion with one source per item, so no `k` is picked), ties breaking on **recency** — the one key genuinely comparable across them, both `created_at` columns being "when we stored it" in unix seconds off one clock. `SearchSource` is a **filter in `BookFilter`'s idiom** (absent is both) and never changes the order; it exists because "search my notes" is a real question while the ordering is never the caller's. **`fts_query` is where a live defect was fixed**: the old `search_notes` bound raw text into `MATCH`, and fts5 reads `-`, `+`, `*`, `(`, `NEAR`, `OR` and a bare `'` as syntax, so `don't` and `C++` failed with a raw sqlx error. Every token is now a quoted phrase; a trailing `*` survives and nothing else does. And **`MATCH ''` raises rather than returning nothing**, so the empty query is a decision and not a shortcut: no hits, no error, no statement issued.
  - **`BookFilter::title` (item 34, no migration).** The sixth predicate, `LIKE` like its neighbours and **deliberately not** the FTS index next door. It has to compose with `count_books`, all five sorts and the offset paging, and `predicate` writes one `WHERE` for the page and the count alike — fts5 would arrive as `books.id IN (SELECT rowid …)` plus a third index with a third maintenance discipline, for one short line of text. It has to behave like the five fields beside it, or a filter struct whose fields match by different rules is one whose callers guess. And **infix is what a shelf filter means**: `possess` finds *The Dispossessed* under `LIKE` and nothing under fts5. `the_title_filter_matches_the_way_its_neighbours_do` is structural — it compares the generated clause against `author`'s — because the behavioural version passes just as well against an FTS predicate that happens to find the same book.
  - **The sort keys get an index, and a writer (item 35, migration `0016`).** There was **no index on any sort key** — the seven that existed were all foreign keys — so every `ORDER BY` sorted the whole table and threw away all but a page, which is what made a deep page expensive and what turned item 18's `books.id` tie-break from insurance into load-bearing. Four indexes; `BookSort::Progress` is the one that cannot have one (a computed ratio across a `LEFT JOIN`) and its `USE TEMP B-TREE FOR ORDER BY` is kept as the **live control** that proves the other four assertions can fail. An indexes-only migration is judged on `EXPLAIN QUERY PLAN` (`0008`'s rule), and `the_sort_key_indexes_are_the_plan_the_planner_picks` reads the SQL `list_books` actually issues rather than an approximation, because the likeliest failure is a *mismatch* between clause and index. **`sort_title` had never been computed by anything** since `0001_init.sql` — a sort-key column added without a writer looks answered and is not, and that reads identically to answered from every call site. It has one now (the title with a leading English article dropped) and it **left `MERGE_RULES` in the same breath**: that table governs what a *record* can carry with a source to attribute, and no provider publishes a filing key, so leaving it there let a record-shaped writer move a book's filing name without moving the title it comes from (`0014`'s "the stored dimensions describe a different image", one column over) *and* let a provider claim a value the derivation had already replaced. It takes the cover metrics' shape instead — one writer, no claim, ignored by every merge — and `only_our_own_columns_sit_out_the_federated_merge` is down to `["cover_path"]`. **`sort_author` lands after two refusals** (items 18 and 20, on the real ground that SQLite cannot parse a human name) because it arrives *inside* the item that adds the index, so the back-fill and the reader come together; `BookSort::Author`'s whole-library-read-then-truncate arm is **deleted, not supplemented**. It is deliberately **not on `Book`** — the engine's filing key is not a fact about the book, and keeping it off the domain type keeps it off the wire. **The encoding is proved, not eyeballed**: `names::sort_key`'s `(rank, last, whole)` tuple packs as `'0' SEP escape(last) SEP escape(whole)` with `SEP = \u{1}`, because a concatenation only compares like a tuple when the separator is strictly less than every byte a component can contain — `escape` buys that with a monotone prefix-free code over `\u{0}\u{1}\u{2}`. SQLite's BINARY collation is `memcmp` and Rust's `Ord for String` is byte-wise, so the two ends compare the *same* way and `the_stored_order_is_the_tuple_order` asserts it over arbitrary lists; a `COLLATE NOCASE` index would have compared differently from the function it caches. **One writer, deriving from the row and not the record**: `refresh_sort_keys` runs last inside the transaction of all four merge writers and reads the *stored* values back, because a merge clause keeps the row's title when the record is silent and a key bound from the record would then describe a title the row does not have — `invalidate_cover_metrics`' rule reached by a different route. `Storage::stale_sort_keys` states the back-fill's work list once (`sort_author IS NULL`, which is *not computed yet* and never *no author*: an authorless book gets a real key whose rank files it last), and `rb sort-keys` is its door, run by `make dev-db`. `BookSort::Title` orders by `COALESCE(sort_title, title)` and the index is on that same expression, which is what let the migration ship with **no SQL back-fill** and keep the article rule in one dialect — an un-back-filled row degrades to its own raw title instead of piling at the top.
  - **Readings (migration `0005`).** `current_page`/`finished`/`date_started`/`date_finished` **left `books`** — that modelled one reading of one book, and rereads are real. `readings` owns them, plus a device-owned mirror (`ko_status`/`ko_percent`/`ko_rating`) refreshed by **straight assignment** like every other device field. `CREATE UNIQUE INDEX idx_readings_one_open ON readings(book_id) WHERE finished_at IS NULL` makes "at most one open reading per book" an **invariant, not a convention**; `open_reading` surfaces its violation as `EngineError::InvalidInput`, never a raw sqlx error. **`Book` keeps all four fields as read-only projections** of the *current* reading (open if there is one, else most recent), resolved by one `LEFT JOIN` in `BOOK_COLUMNS`/`BOOK_FROM` — which is what left `row_to_book`, `render.rs`, `progress_tag`, `progress_text`, the note page auto-anchor and both TUI call sites untouched. Correspondingly **`upsert_book` ignores those four fields entirely**, and its old `finished = MAX(excluded.finished, books.finished)` clause is **retired, not moved**: it only ever existed because reading state lived on `books`, and `a_provider_upsert_never_touches_reading_state` asserts its *absence* so it cannot come back. `update_progress` keeps its book-id signature and opens a reading when none is open — except when clearing `finished`, which reopens the most recent one, or the TUI's finished-toggle would mint an empty reading per keypress. `merge_books` repoints `readings.book_id` inside its transaction and **closes the older of two open readings as `abandoned`** rather than deleting it. The import persists what it had been parsing and discarding: `complete` closes the reading, `abandoned` marks it *without* closing (an abandoned book is one you might pick up), an unknown status leaves ours alone, and **`ensure_reading` opens one only when the book has *none*** — "none open" would make a `complete` sidecar add a reading on every re-import. `attribute_highlights` places a highlight by matching `ko_datetime` into a reading's window and **leaves it `NULL` when no window holds it**: KOReader's sidecar is per-file and a reread appends to it, so the device cannot supply this attribution and inventing it would be worse. **A missing `started_at` is derived, not read as −∞** — an unstarted reading begins one second after the latest `finished_at` of another reading of the same book that is not after its own end. The first cut `COALESCE`d to ±8.64e12, which makes an unstarted reading's window *contain* every earlier one, so the newest read collected the whole book's highlights and the earlier reads held none, permanently and with nothing on screen looking wrong. Both doors in are ordinary: a Goodreads `Read Count > 1` writes several readings with NULL `started_at` **by design** (the CSV has no start date and `goodreads.rs` refuses to invent one), and `record_reading`/`open_reading(.., None, ..)` reach it directly. The `+ 1` is not an epsilon — these are integer unix seconds, so it is the next representable value, and it is what makes a reading own the instant it closed; an *explicit* `started_at` stays inclusive. The `ORDER BY` survives only as a tie-break, since derived windows are disjoint but user-given ones need not be. **`reading_id` is on `Highlight` and reaches every frontend**: `HIGHLIGHT_COLUMNS` selects it, `Engine::highlights_for_reading` is the reading-scoped query (it deliberately *cannot* ask for the unattributed ones — `reading_id IS NULL` is a property of the book's list, not of any reading), `rb highlights` groups by read once there is more than one, and the TUI's highlight list gains a one-cell read gutter (`1`/`2`/`·`) on the same condition — the notes list's `◆`/`◇` shape, and dropped entirely for a book read once, where the column would read `1` on every row. Migration `0005` is the **first destructive migration in the repo** (back-fill, *then* `DROP COLUMN` ×4); `tests/migrations.rs` applies the migrations in two halves to exercise the back-fill, which a fully-migrated database can never reach.
  - **`reading_events` — the activity log (item 21, migration `0011`).** Reading-time data is KOReader-only, so a surface built on it opens to blanks for a library that arrived as a Goodreads CSV. The fix is to consume no source in its own shape: every source writes one row per `(book, day, source)` carrying nullable `minutes`/`pages` and a `confidence` of `measured`/`inferred`, so `statistics.sqlite3` (item 31) and a typed page (item 22) land as one more filler and change no query, no view and no line of frontend. **`day` is TEXT `YYYY-MM-DD` in UTC** — a zero-padded ISO date's lexicographic order *is* its chronological order, so `BETWEEN` is the whole range query, `date(ts,'unixepoch')` writes it and `strftime` reads it, and unlike an integer day number it reads as a date in a `sqlite3` shell without knowing which epoch some Rust file counts from. UTC because `ko_datetime_to_unix` already reads the device's zoneless stamp that way and `attribute_highlights` compares against it; a second convention would put a day and its attribution a boundary apart for anyone not on UTC. **The primary key is `(book_id, day, source)` and `reading_id` is deliberately not in it**, though the grain reads "a book, a read, a date": an event is not an occurrence but the record that a day carried activity, *and* — the fatal half — `reading_id` is nullable `ON DELETE SET NULL`, so a key containing it would need a NULL sentinel and deleting a reading with two events on one day would collide two rows into it, turning an ordinary delete into a constraint error raised by a table nobody touched. The read is therefore an **attribution**, left NULL when a day's evidence does not agree on one, the same call `attribute_highlights` makes. Fillers share one **no-clobber merge** (`EVENT_MERGE`) rather than the device's straight assignment, for `calibre.rs`'s reason: the pattern follows whether a record is *complete*, and each filler is a partial view of the day — the highlight filler has no opinion about minutes. `confidence` is the one non-`COALESCE` field: it ratchets to `measured` and never back, which is what makes the fillers commute. The `DO UPDATE` carries `WHERE {EVENT_DIFFERS}` so `rows_affected` means **changed** rather than seen — without it every refill reports the whole table as updated and idempotency is unobservable, which is the trap the tier-2 corpus fell into. Three fillers need no device (`highlights.ko_datetime` → inferred; `notes.created_at` → measured, and the vault one is the filler no importer can fail to supply; `readings.started_at`/`finished_at` → measured, carrying the **reading's own source**, so a Goodreads `Date Read` lands as `goodreads`). `date()` doubles as the validator — it returns NULL for `2026-13-45` — so `WHERE day IS NOT NULL` is the whole of "no source invents a day". The aggregates (`activity_summary`, `activity_by_day`) are the engine's first reading stats, and **`minutes`/`pages` are `Option`**: `SUM` over all-NULL and over no rows is NULL in SQLite, which is the wanted answer both times, so the absence is carried by the database rather than reconstructed. Counts stay `i64` because they count evidence the engine fully originates. `links_created` is attributed to its **note's** `created_at`, because `note_links` has no timestamp and `set_note_links` replaces a note's whole edge set on every save — a column added there would record the last edit, not the link. Nothing here counts what the user has not done and nothing produces a streak. **Item 31 added a fourth filler and one query.** `Storage::reading_for_day` is the day analogue of `attribute_highlights`, and the window derivation both now share was **extracted into `READING_WINDOWS`** (in `readings.rs`) rather than copied — the ±infinity bug that once gave the newest read every earlier read's highlights is exactly the bug a second copy would reintroduce, and only one of the two would have a test aimed at it. Two calls differ from the highlight version, both deliberate: the test is **overlap, not containment** (a day is 86 400 seconds wide and a read can end at noon inside it, so containment would orphan every day a read ended mid-morning), and a day overlapping **two** windows yields `None` rather than the later one — `attribute_highlights` can prefer the later window because a highlight is an instant and the tie is near-arbitrary, but a day straddling a reread is not a tie, it is a day whose minutes belong to both reads and cannot be split at this grain.
    - **Item 22 added the fifth filler and no query at all**, which is the table's own argument landing for the second time. `Storage::record_typed_page` writes `source = 'local'`, `confidence = measured`, and it is called by **`Storage::update_progress` itself** — two frontends each remembering to log is two frontends that eventually disagree about whether today counted. Four calls there are honesty claims and three are traps an obvious implementation falls into. **A delta needs two points**: the first typed page files the day with `pages: None`, because "you are on page 42" is not "you read 42 pages today" and this is the one place where the difference is a fabricated number rather than a missing one. **Backwards is a correction, not negative pages.** **The day accumulates rather than replaces** — `EVENT_MERGE` is a `COALESCE`, so writing the evening's delta over the morning's would lose the morning silently, and the running total is therefore read back and added to; that also makes re-typing the same page a no-op, which `EVENT_DIFFERS` then declines to touch. And `local` is **its own word rather than the reading's own `source`**: this column's vocabulary is *claimants*, not writers, so a `koreader` reading whose page you corrected this afternoon carries a `koreader` row and a `local` row for the same day, which is exactly what the `(book_id, day, source)` key is arranged to allow. `docs/decisions.md` entry 22 records why `local` was **not** added to `readings.source`.

- **`moments.rs` — the four things worth noticing, and the memory that fires each once (item 23, migration `0017`).** A moment is **recognised, never announced**: every kind here is past tense about something the reader already did, assembled out of rows other features wrote, and nothing in the module is a threshold a frontend could show before it is met. **Nothing about a moment is stored** — `pending_moments` derives the whole candidate set on every ask — because a stored moment is a thing the app can accumulate, and a count of accumulated things is one product decision from the badge `docs/decisions.md` bans. The `moments` table is therefore a set of **opaque ids** and a `surfaced_at`, with no `book_id` beside them: that column would earn an `ON DELETE CASCADE` and cost the rule that nothing derivable is duplicated, and a row outliving its evidence is inert (its moment can never be re-derived) rather than wrong. The id is built by `Moment::id` in Rust and **parsed nowhere else** — not by a frontend, not by SQL — since an id spelled in two dialects eventually differs in one of them.
  - **Two guards, and both err toward silence.** `evidence_at >= books.created_at` is `docs/decisions.md`'s import ruling and needed **no new column**: `created_at` has been on `books` since `0001` and is exactly "when this book entered the library", so a 400-book CSV whose dates are all older than this afternoon mints nothing. It does not cover an *upgrade*, though — a library that has been here for months has honest `created_at`s and reading that came after them, so the first launch would replay a whole reading life — which is what `moment_epoch` answers, one row written by the migration itself. Both are approximations chosen to fail the same way: `books.created_at` is an **upper** bound (`merge_books` folds onto the older row) and a reflection's reach is dated `max(reflection.created_at, target.created_at)`, a **lower** bound, because `note_links` still carries no timestamp of its own. An approximation that can only suppress loses a ceremony; one that can only invent replays a library.
  - **A highlight is dated by `ko_datetime` and never by `highlights.created_at`** — the latter is when the sidecar was read, so a KOReader import would otherwise mint a first-annotation moment for every book in it, which is the CSV failure with a different importer. A stamp SQLite cannot read as a time is no evidence at all, the rule `reading_events`' fillers already follow.
  - **`RunEnded` is the one that had to be argued**, being a hair from the streak this repo bans. It is recognised **only after it is over** (`run_cutoff`: a run ending yesterday is not a moment, because today might continue it), so nothing can be shown while it runs; `RUN_MIN_DAYS` is **2 because that is what "consecutive" means** rather than a bar somebody picked; and its `days` is past tense, the way item 17 permits a count of your own highlights. The per-book guard is applied to the **evidence** — a day counts only if it is at or after the day its book arrived — so an import contributes no days and therefore no runs, without the run code knowing importers exist. The gap-and-islands is a pure Rust function (`runs_of_days`) so the partition is asserted as a *property*: the runs partition the input in order, each is consecutive, and none can be extended.
  - **`acknowledge_moment` is idempotent and deliberately does not re-derive.** `ON CONFLICT DO NOTHING` keeps the first `surfaced_at`, and re-checking derivability would be wrong rather than merely expensive: `RunEnded` depends on the clock, so a moment pending when it was shown can legitimately stop being pending a moment later, and refusing then would replay it for ever. `reading_id` is on `Moment` beside `book_id` because a reread is a second read of one book and anything minted per reading cannot be selected by the book alone.
