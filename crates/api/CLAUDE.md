# crates/api (package `readingbuddy-api`)

Moved here from the root `CLAUDE.md` unchanged.

**This crate is the boundary, and the GUI is its first semantic client.**
`readingbuddyd` links it but never names a method — it moves bytes. The GUI
landed (spec item 25) and found gaps on its first two screens; a gap is an
**engine item**, never a workaround in the frontend.

Three things that pass added here, and each is load-bearing:

- **`Api::open(data_dir)`.** `Api::new` needs an `Arc<Engine>`, so every caller of
  it depends on `readingbuddy`. Harmless for the daemon, which names no method and
  is tempted by nothing; fatal for a semantic client, whose whole discipline is
  that a missing request must be a *compile error* rather than a `use` away.
  `gui/src-tauri/Cargo.toml` lists this crate and not the engine, and CI's plain
  `cargo check --workspace` covers it because the GUI is a workspace member. The
  extra `EngineConfig` knobs are deliberately not parameters: a client that needs
  one is asking for a configuration surface, which is a request on this protocol.
- **`BookDto.reading_status`** — the current reading's own `status`, beside
  `finished` rather than replacing it. Without it *reading*, *abandoned* and
  *never opened* are one `finished: false` with a `current_page`, because
  `abandon_reading` deliberately leaves the reading open. The two ways to recover
  the distinction above this layer are one request per row, or a client-side join
  of `currently_reading` — row-state derivation, which `gui/CLAUDE.md` bans by
  name. A `String`, so an importer can write a status this build does not know.
- **The `ts` feature and `make ts`.** Off by default: it is a *build-time tool*,
  not a capability of the surface, and iOS links this crate in-process with no use
  for a TypeScript emitter. 97 types carry `#[cfg_attr(feature = "ts", …)]` and
  `scripts/gen-ts.sh` emits one `bindings.ts`. Two things about it are written
  down there rather than rediscovered: **`bigint` is widened to `number`** (Tauri
  IPC is JSON, so an `i64` arrives as a `number` and `JSON.stringify(3n)` throws
  — a `bigint` id is a runtime failure tsc calls correct), and **ts-rs drops
  `#[serde(other)]` on `ErrorCode::Internal`**, so the generated union is
  exhaustive over today's codes while the wire is not. The four warnings that
  names on every run are not silenced on purpose.

- **`ReadingDto.progress` and the loss of `From<Reading>` (item 22).** A screen showing one *named* reading had no honest number on the wire: `BookDto::progress` is `Progress::of_book`, which reads the projections of the **current** read and therefore prints today's numbers under an older read's heading — `progress.rs` says so in its own doc. `Progress::of_reading` was already the right answer and was reachable only by a frontend that links the engine, i.e. by the TUI and not by the GUI, so the GUI's only move was `current_page / page_count` above the API — the row-state derivation `gui/CLAUDE.md` bans, walking into all three hazards `ProgressDto` documents. The pairing is a **derivation and lives in the engine** (`Engine::readings_with_progress` / `reading_with_progress` / `active_reading_with_progress`), because `readings` carries no length and deciding which book's length belongs to which read is not a projection. Above the seam there is deliberately **no `From<Reading> for ReadingDto`**: a bare `Reading` cannot answer the field, and an impl that filled it with `of_reading(&r, None)` would report "no percentage" for every book whose length is perfectly well known. `ReadingDto::new(reading, progress)` is the only constructor.

- **The list surface, and how it grew without moving `API_VERSION` (item 18).** `ListBooks` carries `offset` and `filter` **flat** beside `limit` and `sort`, both `#[serde(default)]`, so a payload written against the old two-field method still means exactly what it did — additive growth is what the version number is arranged to allow, and reshaping `params` into a nested `query` would have spent a version bump on nothing. The *typed* method takes one `BookQueryDto` instead, because `limit` and `offset` are both `i64` and adjacent and that is a swap no type checker catches; `dispatch` assembling the struct from unpacked fields is still pure fan-out, since it decides nothing. **`CountBooks` is its own method rather than a field beside the rows**: a count is a property of the *filter*, a shelf asks it once and pages many times, and bundling would make every scroll pay for a scan of the whole matching set — the sharing that matters is the `WHERE`, which happens in the engine. `Response::Count` is its own shape and not `Id`: an id identifies, a count measures. **`BookSummaries` is the one call a list makes instead of four per row**, counts not marks, one row per id in the order asked. And **`BookDto.shape`** is item 19's `EditionShape` crossing the seam — landed here rather than as a one-field item because the GUI links this crate and not the engine, so item 26's shelf either gets the field or re-derives the arithmetic in TypeScript, which is the precise failure item 19 exists to prevent. Derived and read-only like `progress` and `series_label`, dropped on the way back in with them.

- **`API_VERSION` moved to 2, and item 34 is the first thing that moved it.** `SearchNotes` and `Response::NoteHits` were **removed** rather than left standing beside `SearchMarks`, which answers the same question and more of it. Keeping both would have cost nothing on this number and everything on the guarantee: a client able to ask for notes alone and highlights alone has to merge two rankings, has no rule for doing it, and will merge them by source order — which is precisely what ranking once below the seam exists to prevent, so a second door makes the guarantee optional. The narrowing survives as a **filter** (`SearchSourceDto`, `#[serde(default)]`, absent is both) in `BookFilterDto`'s idiom, because "search my notes" is a real question while the *ordering* is never the caller's. `the_replaced_method_is_gone_from_the_wire` asserts the refusal rather than trusting that deleting a variant produced one. `SearchHitDto` is **internally tagged on `kind`**, the shape `StatusFilterDto` already uses — not two nullable fields, since exactly one row exists and a shape that can represent neither or both is one somebody reads wrong. **`BookFilterDto.title` is additive and did not need the bump**; it rode along with it.

- **`MatchCandidateDto` is a row to show, not a record to write (item 36).** It gained `authors_display` and `publish_year`, and **that did not move `API_VERSION`** — both are `#[serde(default)]`, so a payload written against the three-field shape still parses, which is the additive growth the number is arranged to allow. It had to grow *here* rather than in a frontend for this crate's own reason: the GUI links `readingbuddy-api` and not the engine, so recovering the author above the seam meant one `get_book` per candidate — an N+1 on a list a calibre or Goodreads import produces per *row* — and recovering the name's reading order meant re-implementing `readingbuddy::names` in TypeScript. Hence `authors_display` and **no raw `authors` beside it**: `BookDto` carries both because it is a record that round-trips, and a candidate is neither. **`cover_path` is deliberately absent** — nothing draws a jacket in a chooser today, and when something does, the field is item 20's `cover_shelf_path`/`cover_aspect`/`cover_accent` cluster and not the raw path, so the honest addition belongs to the screen that draws it. **The whole `BookDto` was considered and refused**, since `band` holds the entire `Book` and picking is what created the bug: measured, a `BookDto` for a book with a real description serializes to ~19× a candidate (1846 B against 98 B, and still ~10× with every prose field stripped), and it would put `progress`/`reading_status` on a row whose only question is *which book is this*. Getting the picking wrong again costs one more additive field; `BookDto` costs every import report for ever.

- **Moments cross as a list you poll, with no number on it (item 23).** `PendingMoments`/`AcknowledgeMoment` and `Response::Moments`, and three things about the shape are decisions rather than defaults. **`MomentDto.reading_id` sits beside `book_id`** — item 28 mints a card per *reading* and a reread mints a second beside the first, so a moment identified by its book cannot select between them; it was named by an API audit *before* the item was built, which is the one addition here that would have been expensive later because it changes what a moment is rather than what it carries. **`MomentDto.id` is opaque**: built by the engine out of the rows the moment is made of, handed back to acknowledge, and never parsed — its format is not part of this vocabulary and may gain a kind without moving `API_VERSION`. And **there is no count anywhere on this surface** — no total beside the rows, no `count_moments` to reach for on grounds of cheapness — because a number of things waiting is the badge `docs/decisions.md` forbids; `the_wire_states_no_number_of_moments` asserts the *absence*, including that no such method parses, rather than trusting the author. Acknowledging is idempotent through both doors. **Not a subscription**, for the reason the module doc gives about the mount watcher: a client polls on launch and after a write that could mint one.

- **A scope on the search and on the note list, and `API_VERSION` did not move (item 40).** `SearchMarks` gained `book_id` and `ListNotes` gained `reading_id`, both `#[serde(default)]` — so a payload written before either still parses to the request it always meant, which is the additive growth the number is arranged to allow, and `a_payload_written_before_the_scope_existed_still_parses` asserts it in both methods rather than trusting the attribute. They had to grow *here* rather than in a frontend for the reason this crate exists: `SearchHitDto` and `NoteDto` both carry enough to write the filter above the seam, and **that filter is wrong** — `limit` cuts the global ranked list, so a book view searching the library and keeping its own hits gets nothing whenever the top `limit` marks live in other books. An audit found it before a screen was built on it, which is the second time (`MomentDto.reading_id` was the first) that asking the question early cost one additive field instead of a redesign. **`list_notes` refuses `book_id` and `reading_id` together with `InvalidInput`** rather than preferring one: a reading names its book, so the pair is redundant or contradictory, and the engine's `NoteScope` cannot represent it at all — this is the one place the impossible state is reachable and therefore the one place it is named. A silently ignored parameter would put back exactly what the enum removes.

- **A card can be made, and citations can be asked once (items 45/46), and `API_VERSION` did not move.** Two new methods, no existing one reshaped — which is the whole of what additive means here, and `a_payload_written_before_the_cards_wave_still_parses` asserts it rather than trusting the diff. **`CreateFlashcard` re-reads both ids**: `book_id` and `highlight_id` are two handles a client supplies independently and nothing in the schema stops them naming different books, after which a card sits beside a passage from somewhere else for ever. That is "handles do not cross" applied to a *pair*, and the FK underneath makes it more than tidiness — an unchecked write comes back as `FOREIGN KEY constraint failed`, i.e. `internal` for what is really `NotFound`, the finding `link_foreign_record` already recorded. Its reply is **`Response::Bool`** and not a new shape: `UNIQUE(book_id, word)` dedupes, so *you already had this card* and *a card now exists* are different facts a confirmation has to tell apart. **`FlashcardDto.book_id` is deliberately not `#[serde(default)]`** while `highlight_id` is — the attribute is a *request*-compatibility device and no request carries a flashcard, so a default here would only let an old reply parse as `book_id: 0`, a handle a client follows to a `NotFound` indistinguishable from a deleted book (`pdf.rs`'s rule, one crate over). **`CitationsForNotes` carries ids, not rows.** The screen asking is a book's passage list marking what some note already quotes, and it holds those passages already; `Vec<HighlightDto>` per note would put the reader's private text on the wire once per citing note to draw a tick. `CitationsFor` is untouched and is *not* redundant — it feeds the pane that shows the passages, where the words are the point — and `the_citation_batch_puts_no_highlight_text_on_the_wire` pins the absence. A **new method rather than a `note_ids` beside `note_id`**, because one variant answering both would be a reply whose shape depends on which field a client filled in.
- **The wall gets a list, and it is a new method rather than a wider one (items 43 and 41).** `ListReadingRows`/`CountReadings` and `Response::ReadingRows`, with `API_VERSION` still at 2 and **no existing request reshaped** — which matters more here than the version number does, since `ts-rs` emits a new field as *required* in TypeScript however `#[serde(default)]` the Rust is, so a field added to `ListReadings` would have broken `gui/src/lib/api/client.ts` invisibly. It is also the honest shape: `ListReadings` is one book's history and returns `ReadingDto`; this is a page of the *library* and returns `ReadingRowDto`, which carries a book and a passage beside the reading. **`ReadingRowDto` is a row, not a card** — item 44 refused a `CardDto` because a card is a layout (cover, dates, rating, passage, notes) and a layout is a frontend's composition of facts this crate already serves; this row carries no rating and no notes, and it is shaped by what one round trip must hold rather than by what a card draws. The test of whether it has become one is what would be added next: a card would grow the rating. **The passage is here and still not on `ReadingDto`**, which is item 44's own objection read the right way round — that field would ride the reader's private highlight text along on every row of every `ListReadings`, *including the ones nobody is drawing a card for*, and every row of this list is one somebody is. The **opt-in-flag** alternative was rejected for the reason the read number was: `passage: null` would mean *no marks* on one call and *you did not ask* on another. **`read_number`/`of_reads` are not `Option`s.** `ReadNumbering::number_of` folds *read once* into the same `None` as *unattributed* and *not in this list* — right for the TUI's gutter, and two of those three are facts about a **highlight** and unreachable on a list of readings, so the fold is simply not shipped rather than being documented; a client saying "your second read" asks `of_reads > 1`, the same test the gutter makes. **`ReadingFilterDto` is fallible where `BookFilterDto` is not**, and only because of the year: `finished_in` is one nested `DayRangeDto` rather than two flat optional days (the pair is inseparable, and a half-set span is a question nobody asked), validated by the engine's own `DayRange`, so an inverted range is `InvalidInput` at both doors rather than a confident empty wall — item 33's rule about the activity aggregates reaching a filter for the first time. `ReadingFilterDto.book_id` is what lets the single-book card page ask the wall's question narrowed, instead of `ListReadings` plus N `CardPassage` calls.

- **The years the wall has, and the bool that is not a count (item 51).** `ReadingYears { filter }` → `Response::ReadingYears(ReadingYearsDto)`, additive, `API_VERSION` still 2 and no existing request reshaped — which matters more than the number, since `ts-rs` emits a new field as *required* in TypeScript however `#[serde(default)]` the Rust is, so a field on `CountReadings` would have broken `gui/src/lib/api/client.ts` invisibly. It answers a different question anyway and returns a different shape. The picker it replaced was derived from `ActivityByMonth`, a **proxy in five directions**: `reading_events` gets a row when a read *started*, when a note was written, when a highlight carries a device date, when a device measured minutes, and it keeps the days a since-deleted reading explained — and it holds nothing until `RefillReadingEvents` has run, so a library that never refilled offered no years while plainly having finished books. It takes the same `Option<ReadingFilterDto>` the page and the count take, so the same picker narrows to one book, which the proxy could never do at all. **`ReadingYearsDto.open` is a bool and deliberately not a count**: a wall holds open readings on purpose and they are in no year, so without it the years do not partition the wall — and a number of books-in-progress sitting on a control is one product decision from the badge `docs/decisions.md` bans. `the_year_list_puts_no_count_on_the_wire` asserts the absence over the serialized reply, including that no year carries one; the chip's own figure is `CountReadings { open: true }`, the same round trip every other chip makes. Fallible for `ListReadingRows`' reason and through the identical conversion, so an inverted `finished_in` is `InvalidInput` from both doors rather than a picker that confidently offers nothing.

**the versioned surface, and the boundary `docs/decisions.md` names.** The daemon is a transport wrapper; *this* is the API, which is what keeps iOS — no daemons, ever — able to link it in-process. Depends on the engine, `serde` and `serde_json` and deliberately nothing else: no socket, no runtime flavour, no CLI parser.

- `dto.rs` — serde mirrors with `From<domain>`. **The domain types stay serde-free**, and the reasons are structural rather than stylistic: `Book` carries `OffsetDateTime`, half the reports carry `PathBuf` and `Diagnostic` carries a `Duration`, so a derive would pick each wire encoding *by accident* and then that accident is the API; and every field name would become a public promise, making a rename of `ko_percent` a breaking change rather than a refactor. `DiagnosticKind` is mirrored **in full**, all seventeen variants — flattening it to `{kind, detail}` would throw away exactly what made `Diagnostic` stop being a `String`. A `PathBuf` crosses as `to_string_lossy`, so a non-UTF-8 filename does not round-trip; JSON is UTF-8 and the alternative is base64 on every path.
- `error.rs` — `ApiError { code, message }`, the pattern `Diagnostic` set: a typed `Copy` classification beside a human string, with no source error inside it. `ErrorCode` is **appended to, never renamed**, and `#[serde(other)]` on `Internal` makes an unknown code degrade instead of failing to parse — asserted, not hoped.
- `protocol.rs` — `Request` is **named** (`{"method":"get_book","params":{"id":3}}`), one variant per facade method; `Response` is **shaped**, ~30 variants, because a reply is already tied to its call by `Call::id` and sixty single-use response names would be sixty things to keep in sync for no information. `Reply::to_line` owns the framing: `serde_json::to_string` escapes newlines inside strings, so a note body cannot break a line-delimited frame, and the guarantee lives in the same function as the terminator.
- **The surfacing item closed the gap items 21/29/30/31/32 left.** Everything those five built was engine-only: no DTO, no request. Now `enrich_book`/`set_book_fields`/`field_provenance` (items 29–30), `table_of_contents` (item 32), `import_device_statistics` (item 31), and the activity log's four (`refill_reading_events`, `reading_events`, `activity_summary`, `activity_by_day`, item 21). Two rules from that work are worth keeping. **The two aggregates validate through the engine's own `DayRange`** rather than passing two strings down, because an inverted span makes every aggregate report a confident, wrong zero and this layer must not be able to route around the refusal. And **`series_index` with no `series` is not refused here**, though `rb set` refuses it: a rule implemented at the seam is a rule the in-process caller never meets, which is this crate's own argument about `dispatch` applied to a DTO.
- `lib.rs` — `Api` over an `Arc<Engine>`, typed methods, and `dispatch` as **pure fan-out**: one arm per request, unpacking arguments and calling the typed method of the same name. A rule implemented in `dispatch` is a rule the in-process caller never meets, so `dispatch_and_the_typed_method_agree` is asserted for both a read and a write. **Handles do not cross**: `update_note_body`/`delete_note`/`file_path` take an id and re-read the row, because a client echoing back a stale `NoteRecord` would write to a path that had moved. **The mount watcher is deliberately absent** — it is a stream, request/response has no shape for one, and a polling wrapper would give the far side a different debounce from the one `watch.rs` guarantees.
