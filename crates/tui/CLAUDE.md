# crates/tui (bin `readingbuddy-tui`)

The ratatui frontend. Everything below moved here from the root `CLAUDE.md`
unchanged — read the root file first for the product axiom and the repo-wide
conventions.

**The TUI and the GUI are peers and are developed independently** (see
`docs/gui/gui-vision.md`). Work here never obliges work there. Anything both
frontends need belongs in the engine, not copied between them.

## Commands for this crate

- Run it: `cargo run -p readingbuddy-tui` (`--book <selector>` opens straight into a book)
- Inspect the 3D renderer without a TTY: `cargo run -p readingbuddy-tui -- --dump-frame 100x30 [--book X] [--pose YAW,PITCH] [--dump-png out.png]`. The PNG paints each cell exactly as the terminal would (glyph + its two colors), so it shows the quantization rather than flattering past it.
- Ask what the terminal can do (and which renderer that picks): `cargo run -p readingbuddy-tui -- --probe`. Prints the raw reply bytes too, which is the only thing that settles a surprising verdict. Needs a real tty and, inside tmux, the **active** pane.
- See the composed TUI layouts as text: `cargo test -p readingbuddy-tui -- --ignored --nocapture print_layout`
- See the ambient background as text: `cargo test -p readingbuddy-tui -- --ignored --nocapture print_ambient` (each motif at three frames). Its cost: `cargo test --release -p readingbuddy-tui -- --ignored --nocapture ambient_wire_rate`.
- Time either raster (release only, the caps depend on it): `make perf` runs all five reporting sweeps serially — `glyph_cost`, `glyph_wire_rate`, `raster_cost`, `frame_budget`, `wire_rate`. Serial matters: run in parallel they time each other's contention and the pixel traces read 20-30% slow.
- Compare what each renderer costs, terminal included: `make bench`. Needs a real, **active** pane and a book with a **real cover**; it warns rather than silently producing flattering numbers when either is missing. Output lands in gitignored `perf/`: a timestamped per-frame `.jsonl` + `.txt` summary per run, plus `history.tsv` appended one row per mode per run. `make bench-trend` prints the history aligned. `make perf` runs the release-only raster/wire-rate sweeps into the same dir. Knobs are make variables, not flags on `make`: `make bench BENCH_REPS=3` (repeat, modes interleave), `BENCH_ARGS="--book x"`. Byte columns are deterministic at one rep; **latency columns are not** — re-run a surprising one at 3 reps before believing it.
- Same comparison without giving up your terminal: **`make bench-box`** (`scripts/bench-sandbox.sh`). Runs the bench inside a disposable kitty (pinned font + window) hosting its own tmux server (`-L rbbench -f /dev/null`), against a *copy* of `database/`, so it touches neither your panes nor your library and needs no tty of yours — which is also how anything other than a person at a keyboard runs it. Refuses to start above `LOAD_MAX=2.0` (1-min load; `FORCE=1` overrides and the latency columns become suspect). **`env -u TMUX -u TMUX_PANE` is load-bearing**: inherited, they make the app DCS-wrap its queries and the fresh kitty swallows them whole, so every mode silently falls back to glyphs. Rows land in the same `history.tsv` tagged `env=box` — **trend box against box, never against `env=live`** (different font, size, neighbours). Defaults to **3 reps, and rep 1 is the terminal's warm-up**: a freshly launched kitty has never been sent an image, so `rich-always` reads 3.7ms p50 in rep 1 against 7.8-10.6ms in reps 2-3 of the same run, byte columns identical throughout. Not occlusion (reproduced with the window visible), and the in-process warm-up cannot reach it. Its acceptance test is the same calibration: if `rich-always` does not separate from `glyph` **by rep 2**, the box's latency columns are void. History also carries a `load1` column now, so a strange row stays diagnosable.

The suite is **fully headless** (ratatui's `TestBackend`), so a cloud thread can
show what a layout change looks like. Only `make bench`, `make bench-box` and
`--probe` need a real, active pane.

## The crate

Screens: **home** → menu → (library list | search | device | calibre | goodreads | settings) → single-book view. The menu carries the global/CLI actions (search+add, add-by-ISBN, KOReader import, device, calibre, goodreads, settings, remove-from-library). `m` returns to the menu from anywhere; the book view's key bar is always present (`o` expands it — never hide it entirely, or the view becomes a dead end). Modal input flows layer on top of any screen and are routed in `app::dispatch_key` in priority order `help → note_editor → input → confirm → map_key_on`: `ui/textedit.rs` is the in-house multi-line note editor (Enter saves, Esc cancels, Shift/Alt+Enter or Ctrl-J = newline — **there is no `$EDITOR`/suspend path**, deliberately, after a broken vim killed the TUI); `ui/input.rs` is a single-line box (search query, ISBN, progress page, the optional note-page prompt). Notes anchor to a `page`/`location`/`highlight` — the CLI auto-fills page from `current_page`, the TUI asks after the body (empty/invalid/Esc = no page).

- **`s` cycles the library's order, and `ui::library::Sort` is a *frontend* sort — not a fifth `BookSort`.** Four orders: `Recent` (the default, and a **no-op** — the engine already returned the list that way, and re-deriving it here would be a second opinion about an order we were given), `Title`, `Author`, `Year`. `refresh_library` still fetches `BookSort::LastModified` and applies this **beside the filter**, which is the decision: a SQL `ORDER BY … LIMIT 200` would make the sort key decide *which* 200 books are on screen, so pressing `s` would swap the list's contents rather than reorder them. It is also the only place `Author` can live at all — "alphabetically by last name" is a parse of a human name and SQLite has nothing to parse one with. `last_name` handles the four shapes a real library contains: `Surname, Given` (already inverted — **unless the comma is only holding a suffix**, or "Martin Luther King, Jr." files under Martin), dropped suffixes, particles (`Le Guin`, `van Gogh`, `de Beauvoir` — matched case-insensitively, since the same particle is capitalised in one language and not the next), and the last word otherwise. **Articles are not stripped** from titles: a catalogue files "The Overstory" under O, but this list *shows* the string it is sorting by, and a row reading "The Overstory" between "Sea of Tranquility" and "Trust" looks like a bug no matter how right the cataloguing is. Every arm ties, and `sort_by_key` is stable, so a tie keeps recency underneath — within an author, newest first, for free. Missing author/year sort **last** via a leading flag in the key, never first under an empty string. The border always names the order (state persists and is visible), the cursor **follows the book rather than the index** (a cursor that stays on row 3 while the rows move is the app silently choosing a different book, and the next key might be `d`), and the choice persists in `tui.toml`. `s` is global in `map_key` — the same shape as `a`, which only the settings screen answers — and safe to take *because* the three import shelves claim `s` for `Sync` in their own maps, which run first. `cycle_library_sort` = `advance_library_sort` + `persist_config`, split for the same reason `config_snapshot` is split off: the write goes to the user's real `~/.config/readingbuddy/tui.toml`, so tests drive the inner half.
- **`ctrl-d` / `ctrl-u` jump `PAGE` = 12 rows, and `app::Move` is why that is a type rather than an `isize`.** `Move::Row` wraps and `Move::Page` **clamps**, which is the single difference between the arms: `j` off the bottom coming back to the top is how every list here has always behaved and costs one keypress to undo, while a jump doing it flings you to the far end of the list you were paging *through*. Clamping is also what gives the jump a meaning on a list shorter than a page — go to the last row — and `Move::land` is the one place either rule is written, shared by all eight `step_*` methods plus the link picker. **Twelve rows and not the drawn height**: every list here is shrink-wrapped, so "a screenful" is a different number per screen, per terminal, and changes under the user when a filter narrows the list — a jump that moves a different distance each time is one nobody can aim. The keys live in `map_key`'s **control** branch (`PageUp`/`PageDown` map there too, since that is what those keys already mean), which is also what makes them unshadowable: `claimable` refuses any key with Control held, so the three import shelves cannot claim them the way they claim `x` and `r`. The book view pages an *open section's* list only — the section menu is four rows, where a jump either does nothing or lands where one press already does.
- **Deferred work: `pending_scan` / `pending_pull`, drained by the loop, never the key handler.** Every other engine call in this crate is awaited inline in `dispatch_key`, which is fine for a lookup and ruinous for a scan of several hundred sidecars or a sync of forty books — the draw loop and the 20fps ticker would both stop. `App::pump_deferred` does **one unit per loop iteration** (verify → scan → one book of the pull queue), and `run` calls it *after* the redraw, so the frame that says "scanning…" / "bringing 12 books across…" is on screen before the work that blocks. `select!` gained `biased` plus a `std::future::ready(())` arm guarded on `has_deferred()`: without it the queue would advance one book per 50ms tick, and without `biased` a keypress would stop being seen first. A `for` loop in the handler gives neither the progress nor the reachable `select!`. Guarded by `a_sync_drains_one_book_per_iteration`, which asserts the queue *shrinks across pumps* rather than completing in one.
- **The mount watcher is an arm of that same `select!` (item 11), and `App::on_mount_event` only *queues*.** `run` takes an `Option<MountWatcher>` — a machine that cannot watch is a machine that still runs the app — and `next_mount` returns `pending()` forever rather than `None` when the source dies, because a `select!` arm that resolves immediately and forever is a spin. The arm sits **below the keypress and above the ready-arm**: a device plugged in mid-sync is still noticed, and never in front of a keystroke. What it does is deliberately small. An arrival **refreshes the device screen through `pending_scan`** — the same deferred walk `r` does — and only when that screen is what is being looked at *and* it is not already showing a different reader; a `DevicePath` prompt is closed by an arrival, because that is the question it was asking rather than a decision taken off the user. Everywhere else it is a status line naming `m`: being pulled off the book you are reading because a cable was plugged in is the other way to get this wrong, and it is worse. A departure empties the shelf it was showing (those rows name files that are gone) but **keeps `device_root`**, so `r` after replugging still means something. **It never syncs** — `a_reader_arriving_never_brings_anything_across_by_itself` drains every deferred unit and asserts the library is unchanged.
- **`animating()` is not widened for this screen either** — same rule as the ambient layer. The device screen inherits the ambient background for free from `ambient_visible()` (`motif != Off && screen != Book`), which is exactly why its list box and its candidate chooser both `Clear` first.
- **`crates/tui/src/ambient.rs`** — the slow background layer for the **non-book** screens (menu/library/search/settings). `Motif` is `Off | Motes | Contours`, a user setting persisted in `tui.toml` and cycled with `a` on the settings screen; **`Off` is the default**, so the app never starts animating unasked. Never runs on the book view: the object owns that pane, which also keeps the kitty hybrid entirely out of scope.
  - **`animating()` is not widened, ever.** It means "the book is turning" and feeds `params.moving`; fold the ambient layer into it and a parked book reports moving forever and never transmits its crisp frame — with nothing on screen looking wrong. The layer has its own `ambient_visible()` (drawn) / `ambient_animating()` (drifting; frozen under a modal, so opening an input box calms the background rather than making it vanish), and `tick()` splits into `tick_book` + `tick_ambient`. Guarded by `ambient_dirties_without_claiming_the_book_is_moving`.
  - Runs at **`AMBIENT_FPS` = 4, not the 20fps tick**: `advance` reports a change only when the quantized frame index moves, so 4 ticks in 5 cost one integer compare. Same trick as `present.rs`'s pose buckets.
  - Draws through **`blit::blit_sparse`**, a second path beside `blit` (never a replacement — same rule as `raster.rs` beside `render`): coverage-forced split, no `O(2^n)` error search, and uncovered cells left untouched so it composites. Every screen's content box must `Clear` first — a `Block` styles the cells it doesn't draw but never blanks them.
  - **Contour lines are one flat ink, and that is a cost control.** ratatui's diff only skips byte-identical cells; a brightness ramp gave each cell a slightly different averaged colour every frame and repainted the whole terminal — 0.419 MB/s at 200x50, against 0.131 for a full glyph book spin. Flat ink plus a lower `FREQ` took it to **0.019**; motes are 0.006. Bounded by `the_ambient_layer_stays_inside_its_byte_budget`, reported by `ambient_wire_rate`. Ink is the accent pulled to a mid-tone: the terminal background is unknown, so **brightness cannot fade a mote to invisible** — motifs disappear by dropping coverage instead.
  - Line width is normalized by the field gradient (`LINE_HALF_WIDTH`, in *subpixels*). Without it the band's on-screen width tracks the local gradient and the whole thing renders as speckle rather than curves. The noise is made isotropic by scaling the vertical frequency by `4 / cell_h` — an octant subpixel is square, a quadrant one is twice as tall.
